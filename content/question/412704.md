  body_markdown: "Hi @vultran1410 \n\n\n\n> .1.   Does the callback-group-level executor\
    \ concept apply in micro-ROS? I see that it has been merged into ROS2 rclcpp,\
    \ \n>       but since micro-ROS doesn't support rclcpp, I'm a bit confused.\n\
    No, the callback group-level Executor is only available in rclcpp, aka ROS 2.\
    \ However, you don't need callback groups in micro-ROS (rclc): In ROS 2, you can\
    \ only add nodes to an Executor, if you add multiple communication objects, like\
    \ subscriptions, to a node, all subscriptions are added to the Executor. If you\
    \ want to use different priorities for executing the callbacks WITHIN a node,\
    \ this was not possible in ROS 2. Therefore, you can create a callback group and\
    \ assign subscriptions to it. And then add a callback group to an Executor. \n\
    \nIn micro-ROS, there is no hierarchical structure of subscriptions, nodes, executor\
    \ ... like in ROS 2: \n\n    subscription0 --> node0 --> executor0\n\n    subscription1\
    \ --> node1  \n    subscription2 --> node1  \n    subscription1 --> callback_group1\n\
    \    subscription2 --> callback_group2\n    callback_group1 --> executor1\n  \
    \  callback_group2 --> executor2\n\nbut it is flat, that is you can direclty add\
    \ subscriptions to an Executor: \n\n    subscription0 --> node0\n    subscription1\
    \ --> node1\n    subscription2 --> node1\n    subscription0 --> executor0\n  \
    \  subscription1 --> executor1\n    subscription2 --> executor2\n\nThat is, you\
    \ add directly subscriptions to executor. You don't need a callback-group in micro-ROS.\
    \ \nOf course, I agree it would make sense to have the same API in ROS 2 as well\
    \ as in micro-ROS. I could think of a thin-API that would mimick a callback group,\
    \ just to have the same API as in ROS 2, but essentially it would also just add\
    \ all subscriptions of the callback group to the Executor. \n(I will update the\
    \ documentation in micro-ROS accordingly).\n\nWhat would you prefer? Is it okay\
    \ for you, if you could add subscriptions to an Executor directly? \n\n> .2. In\
    \ the rclc repo, it mentioned that \"The software is not ready for production\
    \ use. It has neither been developed nor tested for a specific use case.\". Does\
    \ that mean micro-ROS is also not ready for production use? Does rclc executor\
    \ included in the releases of ROS2 Humble and Rolling version?\n \nThis is rather\
    \ a liability exclusion. It has been used in several commercial products. All\
    \ unit tests are running successfully for Foxy, Humble, Rolling. We achieve [ROS\
    \ 2 Quality Level 2](https://github.com/ros2/rclc/blob/master/rclc/QUALITY_DECLARATION.md)\
    \ for the rclc library. \n\n> Does rclc executor included in the releases of ROS2\
    \ Humble and Rolling version?\n\nthe rclc-package is not part of the default ROS\
    \ 2 distribution, but you can install the binary package like any other ROS 2\
    \ package with e.g. `sudo apt-get install ros-humble-rclc`. [micro-ROS supports\
    \ ROS 2 distrubutions: Foxy, Humble, Rolling](https://github.com/ros2/rclc/#bloom-release-status-of-code-repository-ros2rclc)\n\
    \n>  .3. In the concept page, it mentioned that \"Multi-threaded executor with\
    \ assignment of scheduling policies of underlying operating system.\" is a future\
    \ work with an open PR. Later, there was an announcement about micro-ROS multithreading\
    \ support. Is it the same as the multi-threaded executor mentioned in the concept\
    \ page? If not, what are the differences?\n\nNo. These are different things. \
    \ The multi-threaded Executor will support processing subscriptions in different\
    \ threads (with different real-time priorities) via rclc-API.\n\n I am currently\
    \ working on a branch to re-structure the rclc-Executor, so that it can support\
    \ single-threaded, multi-threaded (POSIX), and non-POSIX (AUTOSAR) operating systems.\
    \ working branch: [restructured-rclc-executor](https://github.com/micro-ROS/rclc/tree/feature/restructured-exectutor).\
    \ \n\n\"micro-ROS multithreading support\" revers to the fact, that the micro-ROS\
    \ client (with its XRCE-DDS middleware) is thread-safe. That means, you can create\
    \ multiple threads, in these threads create multiple micro-ROS clients (with e.g.\
    \ subscription, executors, etc.). The multi-threading support is on the level\
    \ of the middleware. On API level, you have only a \"single-threaded\" Executor.\
    \ But you could create multiple \"single-threaded Executors\" in different threads.\
    \ \n\n>  Can you use C++ user code on top of the rclc? (for both case of using\
    \ rclc with ROS2 and rclc with Micro-ROS)\n\n\nYes, you can always call a C function\
    \ from C++ code. There are limitations regarding full C++ semantics for e.g. callback\
    \ functions. But you can use a static C++ member class method as a callback function.\
    \ See [this example](https://github.com/ros2/rclc/tree/master/rclc_examples#subscription-callback-with-c-class-method).\
    \ Additionally, you can [add a context pointer to a subscription](https://github.com/ros2/rclc/blob/3b4ff9e46ad63ca08a1131760a86b0f42c2bba63/rclc/include/rclc/executor.h#L276).\
    \ Then its callback function is called with the new message and has this pointer\
    \ as a parameter. \n\nSee also the open [issue#126](https://github.com/ros2/rclc/issues/126)\
    \ about a discussion to provide a C++ API for rclc.\n\nYou can use rclc from ROS\
    \ 2 (using any DDS middleware) or as a micro-ROS client on a micro-controller\
    \ (using XRCE-DDS middleware). the rclc-package depends only on the rcl layer\
    \ and does not require anything specific from the underlying middleware."
