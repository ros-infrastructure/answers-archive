  body_markdown: "As mentioned in the [error message](https://github.com/ros/geometry_experimental/blob/5a2b08bfe326d6f94c77d1b7a1cd1577f11c06e6/tf2_ros/include/tf2_ros/buffer.h#L134\
    \ ) \"If you have a seperate thread servicing tf messages, call setUsingDedicatedThread(true)\
    \ on your Buffer instance.\" This will allow your queries to succeed. \n\nSince\
    \ you are manually populating the data you should be setting usingDedicatedThread(true).\
    \ This is a protection that allows tf to error instead of always timing out after\
    \ the full timeout in a single threaded process. \n\nYou are correct that [here](https://github.com/ros/geometry_experimental/blob/12605ab6b8024395c014e76ecc9b75d853c5c631/tf2_ros/src/buffer.cpp#L54)\
    \ and [here](https://github.com/ros/geometry_experimental/blob/12605ab6b8024395c014e76ecc9b75d853c5c631/tf2_ros/src/buffer.cpp#L64)\
    \ the return of canTransform is not used. This is because the only function there\
    \ is to do the timeout, without generating any error messages (which is much less\
    \ computationally intensive.) After the timeout has passed, lookupTransform will\
    \ requery and either generate the result or produce the error message. \n\nIt\
    \ is possible to implement a fully parallel path for the non-timeout methods,\
    \ but at the higher level to decrease code complexity the non-timeout methods\
    \ simply call the timeout methods with zero timeout. The ability to do query without\
    \ timeouts was never a design goal from a use case but was a requirement of separating\
    \ the core library from the ROS interface which abstracts time. "
