  body_markdown: "This is where you create multiple workspace overlays (i.e. `catkin_ws`s)\
    \ and use [workspace chaining](http://wiki.ros.org/catkin/Tutorials/workspace_overlaying#Chaining_catkin_workspaces).\n\
    \nDepending on wether you use `catkin_make` or `catkin tools`, the workflow is\
    \ a bit different. I'll demonstrate this with `catkin_make`.\n\n1. create your\
    \ first workspace, i.e. where you put your package A, as you normally would:\n\
    \        \n        $ mkdir ~/catkin_ws_A\n        $ cd ~/catkin_ws_A\n       \
    \ $ <PUT PACKAGE A IN HERE>\n        $ source /opt/ros/<ROSDISTRO>/setup.bash\n\
    \        $ catkin_make\n1. create another workspace for package \n\n        $\
    \ mkdir ~/catkin_ws_B\n        $ cd ~/catkin_ws_B\n        $ <PUT PACKAGE B IN\
    \ HERE>\n        $ source ~/catkin_ws_A/devel/setup.bash   <----- This is the\
    \ important difference!\n        $ catkin_make\n\nNow, you can compile both workspaces\
    \ independently and B has Access to A (but not the other way around!). Also note\
    \ that you have to compile first `catkin_ws_A` and then `catkin_ws_B` if you change\
    \ something in package `A`, thus that it takes effect. \n\nNote that you have\
    \ to `source ~/catkin_ws_B/devel/setup.bash` to accomplish this. Just sourcing\
    \ `caktin_ws_A` will be your regular one workspace layout.\n\nThere are some side-effects\
    \ regarding build artifacts, thus I'd recommend you read the wiki page linked\
    \ above (section 4) carefully. But all in all, this works pretty well.\n\n\n------\n\
    **EDIT**\n\nWhen you already have two workspaces, make sure to delete any `build`/`devel`/`install`/`logs`\
    \ folders in `caktin_ws_B`, as well as the top-Level `CMakeLists.txt`. You need\
    \ to create the chaining from a clean workspace. And don't to forget to `source\
    \ ~/catkin_ws_A/devel/setup.bash` before  calling `catkin_make` in `caktin_ws_B`\
    \ in the same terminal."
