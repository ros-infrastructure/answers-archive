  body_markdown: "Based on your nav2 settings from your github issue (https://github.com/ros-planning/navigation2/issues/2537),\
    \ it looks to me like the sensor data is not set up correctly. \nMaps don't make\
    \ anything by themselves, they use plugins to fill the data, which in turn use\
    \ sensor data to fill plugins. The total result is the stack of data of all plugins,\
    \ from any sensor input. It's a very elegant system imo, but requires some setup.\n\
    \nIt looks to me like you have a lidar on your robot which you want to use for\
    \ mapping. Since the global map seems to work, we can use this as a template and\
    \ work from there.\n\nIn your local costmap, the plugins are a `VoxelLayer` and\
    \ an inflation layer. Voxels are used for 3d mapping, and I would think that you\
    \ are looking for an `ObstacleLayer`, same as you use for your global map. You\
    \ can copy the obstacle layer from your global costmap onto your local costmap,\
    \ and remove the voxel layer. I suggest the following:\n\n    local_costmap:\n\
    \      local_costmap:\n        ros__parameters:\n          update_frequency: 5.0\n\
    \          publish_frequency: 2.0\n          global_frame: odom\n          robot_base_frame:\
    \ base_link\n          use_sim_time: False\n          rolling_window: true\n \
    \         width: 3\n          height: 3\n          resolution: 0.05\n        \
    \  robot_radius: 1.0\n          plugins: [\"obstacle_layer\", \"inflation_layer\"\
    ]\n          inflation_layer:\n            plugin: \"nav2_costmap_2d::InflationLayer\"\
    \n            cost_scaling_factor: 3.0\n            inflation_radius: 0.55\n \
    \          obstacle_layer:\n            plugin: \"nav2_costmap_2d::ObstacleLayer\"\
    \n            enabled: True\n            observation_sources: scan\n         \
    \   scan:\n             topic: /scan\n             max_obstacle_height: 2.0\n\
    \             clearing: True\n             marking: True\n             data_type:\
    \ \"LaserScan\"\n         static_layer:\n            map_subscribe_transient_local:\
    \ True\n          always_send_full_costmap: True\n      local_costmap_client:\n\
    \        ros__parameters:\n          use_sim_time: False\n      local_costmap_rclcpp_node:\n\
    \        ros__parameters:\n          use_sim_time: False\n \nThe local costmap\
    \ is necessary for autonomous driving, so I hope that you can get your robot working\
    \ with this fix. "

    \ nodes, then it works.\n\nPer https://docs.ros.org/en/rolling/Concepts/Intermediate/About-Quality-of-Service-Settings.html\n\
    A map_server publishing as \"transient_local\" should be readable by subscriber\
    \ as volatile, but this doesn't seem to work in humble. \n\nSee discussion at\
    \ https://github.com/ros2/ros2/issues/464\n\nTo see old messages, the subscriber\
    \ also needs to be \"transient local\".\nNav2 costmap subscribes as \"volatile\"\
    \ (at least in humble), so it does not see the old map. "
