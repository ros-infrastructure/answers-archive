  body_markdown: "Please correct me if I'm wrong, but my understanding is that you\
    \ want to modify and rebuild a specific package that you presumably installed\
    \ as a debian binary (`apt install ...` or similar) since it is on `/opt/ros/...`.\
    \ \n\nThe source code is not packaged with C++ debians, only the headers. So you\
    \ would need to clone the package in question to a [workspace that you could then\
    \ overlay](https://docs.ros.org/en/foxy/Tutorials/Beginner-Client-Libraries/Creating-A-Workspace/Creating-A-Workspace.html#background)\
    \ on top of your binary install. \n\nBear in mind that this would require you\
    \ to also rebuild any packages that depend on the package that you modified (e.g.\
    \ I believe you would also need to rebuild the various `ros2_controllers` that\
    \ depend on the `controller_interface`\n\nPutting that into practice could look\
    \ like:\n\n    # create a source workspace \n    mkdir -p ~/control_ws/src\n \
    \   \n    # go to your src folder and clone the repo/branch that you will be modifying\n\
    \    cd ~/control_ws/src\n    # optionally fork the repo first to track your independent\
    \ changes and be able to make a pull request later on\n    git clone https://github.com/ros-controls/ros2_control.git\
    \ -b foxy\n    git clone https://github.com/ros-controls/ros2_controllers.git\
    \ -b foxy\n    # git clone ... for any other packages that depend on controller_interfaces\n\
    \    \n    # make your changes to any of the files\n    \n    # build the workspace\n\
    \    cd ~/control_ws\n    colcon build --symlink-install\n    \n    # source the\
    \ workspace - this step is crucial to make it so that you're system will actually\
    \ use the modified packages rather than the original debs\n    # you can optionally\
    \ add this step to your ~/.bashrc to \"permanently\" overlay this over your binary\
    \ installation\n    source install/setup.bash\n    \n    # Optional but appreciated\
    \ - if you think the community would benefit from your changes, make a Pull Request\
    \ to propose your changes be added upstream\n\n"

  - body_markdown: |-
      I'm not  sure what exact change OP wants to make  to the code, but: If you're adding new API or breaking the ABI then yes, you will need to rebuild everything downstream. But if you just change functionality inside the library then you should be able to rebuild the single package in the overlay workspace, and if the setup paths are working correctly then the new shared library will be loaded at runtime instead of the old installed one.

      Although, due to https://github.com/ros2/ros2/issues/1150 it may not be trivial to overlay the Foxy core libraries properly, not sure.

      Note: one could always build the whole thing from source - it takes a little time but it's not so bad.
