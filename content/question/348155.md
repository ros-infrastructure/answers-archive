    Hi @Ivan4815162342,

    Since the [Gmapping](http://wiki.ros.org/gmapping) node will only take as input [sensor_msgs/LaserScan](http://docs.ros.org/api/sensor_msgs/html/msg/LaserScan.html) you will need to convert the sonar data, generally speaking given in [sensor_msgs/Range](http://docs.ros.org/melodic/api/sensor_msgs/html/msg/Range.html) into that particular LaserScan msg type.

    This topic was already treated in some others post in the forum like [here](https://answers.ros.org/question/265113/converting-sonar-ranges-to-laserscan-message/) and [here](https://answers.ros.org/question/264938/converting-ultrasound-range-to-a-laser-scan/). Maybe you find usefull those.

    On the other hand, take into accout that Gmapping is designed to have one sole input; thus in order to use more than one sensor data you will need to unify the msgs into one topic. Tools like [this](https://github.com/ipa320/cob_driver/tree/indigo_dev/cob_scan_unifier) one  can be used for that purpose.

      Well, as I said, unfortunatelly Gmapping only takes one LaserScann input, thus, either you convert your sonar data into a LaserScann and merge it with your laser sensor data to feed the Gmapping node or you use another SLAM paradigm different from Gmapping. Nevertheless, the vast mayority of SLAM nodes on ROS uses a unique LaserScann input like [hector_slam](http://wiki.ros.org/hector_slam).

      Things like [this](https://github.com/RiccardoGiubilato/ros_autonomous_car/blob/master/src/sonar_to_laser.py) and [this](https://github.com/alexsleat/projectChimaera/wiki/Other-Sensors-and-ROS-gmapping-(SLAM)) can help

      But using Sonar data for mapping is not a normal thing to do, based on its [multiple problems](https://answers.ros.org/question/41550/mapping-with-sonar-data/) and drawbacks. Furthermore, why do you want to use sonar data in the first place if you have a laser sensor that is a lot more precise. With the laser data will be sufficient to generate a good map.
