    \nI'll only briefly touch some of the questions, as they are pretty generic and\
    \ thus would require quite a lengthy discussion (at least, some of them).\n\n\
    >  is diagnostics the recommended way to do what I'm trying to do\n\nThat ones\
    \ easy, at least: Yes (in the ROS ecosystem, anyways) :-)\n\n>  it feels somewhat\
    \ verbose for a \"simple\" task\n\nTrue, then again, you should not be using the\
    \ raw diagnostics but use [the `diagnostics_updater`](http://wiki.ros.org/diagnostic_updater)\
    \ as this highly simplifies the required code. It is not clear, if you have done\
    \ this. There are also helper classes/functions that specifically deal with publishers\
    \ [(check the example, l. 191-211)](https://docs.ros.org/api/diagnostic_updater/html/example_8cpp_source.html#l00191).\
    \ Note that you also [need to call `tick()` function on the respective updater\
    \ for each `publish`](https://docs.ros.org/api/diagnostic_updater/html/example_8cpp_source.html#l00239).\
    \ All in all, this should be like 5 lines of code, I don't feel that this is overly\
    \ verbose.\n\n> for third party drivers, it would be convenient to be able to\
    \ add topic rate monitoring without modifying the publisher\n\nTrue (again). But\
    \ there is no tool (that I know of) that can actually do that. You could achieve\
    \ that by writing something like a generic \"ExternalTopicRateMonitor\" node,\
    \ which subscribes to the topic. But this adds another node and one pub/sub-cycle,\
    \ so it defeats the purpose of the diagnostics (at least, to some extent). It\
    \ could still help you to achieve your goal.\n\n> is it possible to monitor nodes\
    \ based on whether they have ever printed warnings/errors/fatal errors to the\
    \ log?\n\nI'm not quite sure what you expect here. In terms of \"I'll just start\
    \ up something\", AFAIR, no. But then again there is [the `rqt_console`](http://wiki.ros.org/rqt_console),\
    \ which does something pretty similar. So you could check how this is implemented\
    \ therein. Or is that actually already what you want?\n\n> What about nodes that\
    \ crash\n\nSure they cannot update their diagnostics. You could use [a `bond`](http://wiki.ros.org/bond)\
    \ for that. But that would again force you to update the code. Or go the \"ExternalTopicRateMonitor\"\
    \ way again (hoping that this doesn't crash) ;-) \n\nI hope this answers some\
    \ of your questions, but I'll also be interested in other people's opinion..."

Hi.

My goals are

1. to find some way to easily monitor if a sensor driver node is publishing data at the expected rate, and
2. to set up a general monitoring system for my ROS nodes, possibly tied to warning/error logging.

I've been looking into the [diagnostics](https://wiki.ros.org/diagnostics) package and its sub-packages and tutorials. First of all, is diagnostics the recommended way to do what I'm trying to do? I was able to write a test node that publishes something and adds diagnostics for its own publishing rate, and it works, but it feels somewhat verbose for a "simple" task. Also, for third party drivers, it would be convenient to be able to add topic rate monitoring without modifying the publisher (to avoid maintaining a fork of the driver).

For more general monitoring, is it possible to monitor nodes based on whether they have ever printed warnings/errors/fatal errors to the log? So that all nodes with just info and debug to the log are "green", but if you ever print a warning, the node becomes "yellow" at least for a while, and so on.

Thanks.

Edit: A followup:

What about nodes that crash or otherwise fail to run their internal diagnostics? If a drive crashes, it won't for instance update its own topic frequency diagnostics, so on /diagnostics, I suppose the error won't show up. Is that right, and if so, what's the recommended way to solve it?
