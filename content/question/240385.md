  body_markdown: "**TL;DR:** Use a [SimpleActionClient](http://wiki.ros.org/actionlib_tutorials/Tutorials/SimpleActionClient)\
    \ to send a [MoveBaseGoal](http://docs.ros.org/api/move_base_msgs/html/action/MoveBase.html)\
    \ to an instance of the [move_base](http://wiki.ros.org/move_base) node. There's\
    \ a tutorial that shows you how to do this in C++ [here](http://wiki.ros.org/navigation/Tutorials/SendingSimpleGoals)\
    \ or look below for the python equivalent. In the target pose you can specify\
    \ a pose *and* an orientation. What you want to do is calculate the heading between\
    \ \"goalN\" and \"goalN+1\" then send your robot to goalN with that heading. So\
    \ that when the robot successfully gets to goalN it will automatically rotate\
    \ on the spot to face goalN+1. \n\nOf course, MoveBase goals work with any heading\
    \ you provide, so your robot doesn't *have* to rotate to face anything specifically.\
    \ But if your robot is already facing the next goal, that usually ensures that\
    \ the path-planner will plot a straight line directly to it.\n\n\n----------\n\
    \nFull explanation:\n=======\n\nSo you want to achieve a trajectory that looks\
    \ something like this?\n\n![square_odom](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/14699381876035632.png)\n\
    \nI've just managed to achieve this myself, and there isn't really a good explanation\
    \ anywhere of how to do all this so I'll try to quickly run you through it. \n\
    \n### What you will need ###\n\n 1. A **navigation stack** for your robot. Doesn't\
    \ really matter how you do it as long as you have a map, an odometry stream for\
    \ your robot in that map, and an instance of the move_base node. I'm personally\
    \ using the [robot_localization](http://wiki.ros.org/robot_localization) package\
    \ and a pre-made launch file for the move_base node that came with the robot I'm\
    \ using.\n 2. A node which acts as a **SimpleActionClient**. You will have to\
    \ write this yourself, but it's relatively straight forward as long as your navigation\
    \ stack works properly.\n\n### Writing the SimpleActionClient ###\n\nThere is\
    \ already a tutorial on how to do this in C++ [here](http://wiki.ros.org/navigation/Tutorials/SendingSimpleGoals),\
    \ but I'm using Python so that's what my explanation will be in.\n\nEssentially\
    \ the actionlib package is a framework for writing your own goal and feedback\
    \ system. The client sends the goal (usually from your laptop) and the server\
    \ typically runs on the robot, executes the goal and provides feedback. The goal\
    \ can be anything from moving the robot base to moving an arm. There is already\
    \ a simplified version of this package with a few basic goals built in, and this\
    \ is what we will be using. More specifically, we want to use the 'MoveBaseAction'\
    \ goal that tells the move_base node where to send the robot in the world.\n\n\
    The code I use (roughly para-phrased) is here:\n\n    # Important modules to import\n\
    \    import rospy\n    import actionlib\n    from move_base_msgs.msg import *\n\
    \n    # Create your SimpleActionClient and boot a default version of the SimpleActionServer\n\
    \    client = actionlib.SimpleActionClient('move_base', MoveBaseAction) \n   \
    \ client.wait_for_server()\n\n    def send_robot_to_goal(X, Y, heading):\n   \
    \     # Cancel any pre-existing goals (don't want them to conflict)\n        self.client.cancel_all_goals()\
    \    \n\n        # Convert to a heading (yaw) to quaternion\n        yaw = heading\n\
    \        roll = 0.0\n        pitch = 0.0\n        quaternion = tf.transformations.quaternion_from_euler(roll,\
    \ pitch, yaw)\n       \n        # Create a new goal\n        goal = MoveBaseGoal()\n\
    \        goal.target_pose.header.frame_id = 'map'          # The frame you want\
    \ to navigate in\n        goal.target_pose.header.stamp = rospy.Time.now()\n \
    \       goal.target_pose.pose.position.x = float(X)        # X coordinate to travel\
    \ to\n        goal.target_pose.pose.position.y = float(Y)        # Y coordinate\
    \ to travel to\n        goal.target_pose.pose.orientation.x = quaternion[0]\n\
    \        goal.target_pose.pose.orientation.y = quaternion[1]\n        goal.target_pose.pose.orientation.z\
    \ = quaternion[2]\n        goal.target_pose.pose.orientation.w = quaternion[3]\n\
    \n        # Send goal to move_base node\n        self.client.send_goal(goal)\n\
    \nThe heading can be whatever you want, and you can calculate it however you want.\
    \ I think from memory ROS expects roll/pitch/yaw to be of the format +0 >> +180\
    \ >> -180 >> -0 instead of 0 >> 360 degrees. I prefer to work with 0 >> 360 so\
    \ I've written a lot of my own functions for the heading/quaternion calculations.\
    \ \n\nX,Y are the points you want the robot to move to in the 'map' frame. This\
    \ should be the same frame created by your navigation stack, and the one that\
    \ all your odometry data is reported in.\n\nAlso, something to be mindful of,\
    \ the heading the robot will rotate to is it's heading *in the map frame*, which\
    \ may be different from magnetic heading depending on how you set up your navigation\
    \ stack \n\n### Making  move_base plot straight paths ###\n\nAll this by itself\
    \ won't achieve anything unless you understand a little bit about how move_base\
    \ works. If move_base is ordered to move the robot to a point it isn't currently\
    \ facing, it will bring the robot around in a sweeping arc before heading towards\
    \ the goal - as I'm sure you've already seen. \n\nHowever, if the robot is already\
    \ facing the goal, then it will (usually) just plot a path straight to the goal,\
    \ resulting in odometry similar to the image above. \n\nSo, we can force the robot\
    \ to travel everywhere in straight lines by making it face the next point your're\
    \ going to send it to. For every point you want to send the robot to - say \"\
    goalN\", calculate the heading between \"goalN\" and 'goalN+1\" and send your\
    \ robot to the X,Y position of \"goalN' with that heading. **When the robot gets\
    \ to the X,Y coordinate, it will rotate on the spot to face the heading you specified**.\
    \ But the key part being that it will only rotate on the spot **after** you've\
    \ already arrived at X,Y. \n\nWhat I've described uses a single move goal to execute\
    \ a translation (forward movement) and *then* a rotation. In theory of course,\
    \ you can break this down into two separate goals  and reverse the order, i.e.\
    \ a rotation and then a translation. The rotation is just a move goal where X,Y\
    \ are the current X,Y coordinates of the robot in the 'map' frame. However, personally\
    \ I've found this doesn't work most of the time (if told to rotate on the spot\
    \ the robot simply doesn't move), and it's something I'm still working on so hopefully\
    \ I'll be able to update this again soon.\n\nHope this explanation helps."
