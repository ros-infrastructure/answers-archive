  body_markdown: "I understand your question is about thermal images, but I will use\
    \ some information of depth images to provide the explanation, so please bear\
    \ with me.\n\nThere is a very good [tutorial](https://www.stereolabs.com/docs/ros/depth-sensing/)\
    \ from StereoLabs that explains how depth information is visualized:\n\n> If you\
    \ use the Image plugin, since the\n> depth data are published on topics of\n>\
    \ type sensor_msgs/Image it differs from\n> a \u201Cnormal\u201D image in that\
    \ the data is\n> encoded in 32-bit (floating point) not\n> 8-bit.\n> \n> The parameters\
    \ are the same as for\n> Image, with three additions:\n> \n> **Normalize range**:\
    \ Since a floating\n> point image is not directly rendered,\n> it is converted\
    \ to an 8-bit grayscale\n> image. Enabling this field means the\n> normalization\
    \ range is automatically\n> calculated \n> \n>**Min value**: If Normalize\n> range\
    \ is unchecked, you can manually\n> set the minimum depth range in meters\n> \n\
    >**Max value**: If Normalize range is\n> unchecked, you can manually set the\n\
    > maximum depth range in meters Manually\n> setting the normalization range is\n\
    > useful if you know the maximum value\n> measured for the depth and you want\
    \ to\n> keep the image scale static\n\nFurther in REP 118:\nhttps://www.ros.org/reps/rep-0118.html\n\
    \n> **Depth images** are published as **sensor_msgs/Image** encoded as 32-bit\
    \ float. Each pixel is a depth (along the camera Z axis) in meters.\n\nMoreover:\n\
    \n> Alternatively, a device driver may publish depth images encoded as 16-bit\
    \ unsigned integer, where each pixel is depth in millimeters. This differs from\
    \ the standard units recommended in REP 103.\n\nI believe the same is happening\
    \ with your thermal images as they also subscribing to **Image plugin**, take\
    \ a look at this example of thermal sensor: http://wiki.ros.org/optris_drivers\n\
