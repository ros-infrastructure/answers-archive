  body_markdown: "The cause behind this unrealistic interaction (that is, this lack\
    \ of friction) is the use of `PositionJointInterface` for the UR10 joints.  [Here](https://github.com/ros-industrial/universal_robot/commit/6c4318a3c0024be31e919cdd30741456f4eaf778#comments)'s\
    \ a decent explanation of the phenomenon: \n\n> ... using 'set position' or 'set\n\
    > velocity' in gazebo forces the physics\n> simulation to try and accomplish this,\n\
    > which results in strange behavior.\n> It's actually preferable, according to\n\
    > the Gazebo team members I'm working\n> with, to always use 'set force' in\n\
    > Gazebo because that allows a more\n> normal interaction when the commanded\n\
    > force of an arm joint puts the arm in\n> contact with the environment.\n\n \
    \ Following [an example](https://github.com/ros-industrial/universal_robot/commit/6c4318a3c0024be31e919cdd30741456f4eaf778),\
    \ I made local changes to the `universal_robot` package to use `EffortJointInterface`\
    \ instead.  [Some gain values from ARIAC](https://bitbucket.org/osrf/ariac/src/de9f92a60aab743c6c7f8bf273cb732c34a51320/osrf_gear/launch/ur10/arm_controller_ur10_custom.yaml?at=ariac_2017&fileviewer=file-view-default#arm_controller_ur10_custom.yaml-21:28)\
    \ provide decent performance.  Thanks to everyone who contributed suggestions!"

The robot tool is a prismatic gripper with four rods that slip into matching holes on the object to be grasped.  Using this gripper to move the object works fine for motion perpendicular to the rod axes.  In the video, for example, the rods are parallel to the world x-axis so motion in the z-y plane is fine; the robot lifts the object then translates in the negative y-direction okay.  I think the problem is that the friction force is not being computed well because when the robot translates in the x-direction the object seems to stay put until it reaches the end of the rod and then it goes berserk.  (If you look closely in the second video it can be seen that the gripper starts to move to the right and the object stays still.  I guess the object crosses the camera in that video so we get to see the holes and rods inside the object.)

![object and gripper](https://media.giphy.com/media/5gYfovOF9VyrcwA7fl/giphy.gif)

![object and gripper closeup](https://media.giphy.com/media/5UGV4f6H08W0m18PDe/giphy.gif)

There is a second reason I think the friction calculation is to blame: a different pick-and-place simulation I made this year had problems lifting objects via friction.  See [Question 1](http://answers.gazebosim.org/question/19287/friction-insufficient-in-grasping-simulation/), [Question 2](http://answers.gazebosim.org/question/19381/grasping-unable-to-lift-object/), and [Question 3](https://answers.ros.org/question/291228/simple-box-grasping-fails/).

**==========**

**update:** This video where I replaced the gripper with a rigid forklift-type attachment lends weight, I think, to the idea that the problem is due to physics (friction?) and not the ROS controller or something.

![forks instead of gripper](https://media.giphy.com/media/1dJRV2QLTA94szjZL9/giphy.gif)

**==========**

I've tried using all four physics engines and modifying physics tags in the world file, as well as collision surface tags in both the object sdf and the gripper urdf.  It's apparent that changing these parameters has some effect (though mu1 and mu2 don't make any difference) but the problem persists.  The files are pasted below.

It also seems to me that this could be a problem to do with Gazebo 9, which is what I moved to because the previous project had a mobile base that could not move due to [this bug](https://github.com/ros-simulation/gazebo_ros_pkgs/issues/612) with Gazebo 7 and ros_control.  Since this simulation does not have a mobile base I will try reverting to Gazebo 7 to see if that fixes the gripping problem.

**update:** The behavior is identical with Gazebo 7.  I've seen the same thing on two computers running Gazebo 9 and now one computer running Gazebo 7.

An additional tidbit: if the mass of the object is too high (though still less than 1) it will fall during the upward motion.  So that's fun :-/
