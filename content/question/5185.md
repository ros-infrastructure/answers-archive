    The easiest way to do this involves writing a Gazebo plugin. Some functionality like this was built into drcsim; its interface is described in [this tutorial](http://gazebosim.org/wiki/Tutorials/drcsim/2.7/controller_synchronization), though you may have to [dig into the code](https://bitbucket.org/osrf/drcsim/src/default/drcsim_gazebo_ros_plugins/src/AtlasPlugin.cpp#cl-2106) to see how it's working.

    An alternative is to use the gazebo `~/world_control` topic and publish messages to tell Gazebo to take another simulation step when you are ready. I don't think there's any tutorials for how to do this though.

Hi

(Xubuntu, Hydro, Gazebo 1.9).

I have set up Gazebo to simulate a simple mobile robot (camera sensor, driven wheels). I have compiled a ROS node to do some control that requires quite a bit of computation. Now, as best as I can tell, when I start all this together, Gazebo runs along attempting to keep up with the wall clock (and manages that just fine). My controller can read the /clock published by Gazebo and try to keep up. The question is - how can I arrange that Gazebo wait for my controller if my controller takes longer than a fixed time slice to compute?

My first thought is that I should be publishing /clock from my controller, and configuring Gazebo to use this and not publish its own clock. Is this correct? So that if I don't publish the clock for a while Gazebo will just hang? That's what I'd expect, but I can't find - despite plenty of searching - any documentation or tutorial covering this. And it leads to a few other questions, too.

For instance, I am using the standard ROS controller for each wheel "effort_controllers/JointVelocityController", running at 50Hz. If I publish the time t=0.02s, and I haven't yet published the wheel speed for that time, presumably that controller will just use the old speed. So what do I do, I publish the wheel speed first, and then - wait a bit? Before publishing the clock? How do I guarantee the controller has received the new command speed before allowing the simulation to progress?

Hopefully, what I am describing will be a familiar scenario, and someone can point me at some documentation for how to do this sort of thing, since it seems there will be quite a few "little questions" even if publishing /clock from my controller is the right thing to do. Failing that, my other thought was that I could write a plugin for Gazebo that controlled the progression of the simulation and the distribution of signals to the various controllers (or implemented the controllers itself) but I'd much rather not get into that if at all possible...

To deflect one possible criticism, I appreciate that on a hardware robot I can't make mother nature wait, but either (a) for a pure simulation project or (b) during controller development, it seems this must nonetheless be a common problem. Presumably there is a common solution?
