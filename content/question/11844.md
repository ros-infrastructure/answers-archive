  body_markdown: "**Executive Summary**\n\nUse `/diagnostics` to publish hardware\
    \ diagnostics data from **every** device driver.\n\nUse `diagnostics_aggregator`\
    \ to collect and group diagnostics data on any significant system. \n\n**Background:\
    \ /diagnostics**\n\nTo begin with, it is best practice to set up diagnostics on\
    \ all robot hardware at a minimum.  Most of the drivers included with ROS include\
    \ some form of diagnostics messages.  The ROS diagnostics toolchain is not a computation\
    \ graph level concept (like parameters, nodes, or topics), but is instead built\
    \ on top of the `/diagnostics` topic.  \n\nHardware drivers publish to the `/diagnostics`\
    \ topic a [diagnostic_msgs/DiagnosticArray](http://www.ros.org/doc/api/diagnostic_msgs/html/msg/DiagnosticArray.html)\
    \ message, which contains a header (sequence number, timestamp, and frame_id)\
    \ and an array of [diagnostic_msgs/DiagnosticStatus](http://www.ros.org/doc/api/diagnostic_msgs/html/msg/DiagnosticStatus.html)\
    \ messages.  \n\nThe `DiagnosticStatus` contains:\n\n - `byte level` - One of\
    \ three states (OK, WARN, ERROR), which represents the overall hardware health.\n\
    \ - `string name` - The name of the device this `DiagnosticStatus` represents\n\
    \ - `string hardware_id` - A unique hardware identifier, possibly a serial number\
    \ or UUID\n - [diagnostic_msgs/KeyValue[]](http://www.ros.org/doc/api/diagnostic_msgs/html/msg/KeyValue.html)\
    \ - An array of key/value pairs used to represent any additional pertinent information\
    \ about the sensor. (For example \"temperature\":\"35C\", \"frequency:100Hz\"\
    , \"voltage:24V\")\n\nAny node subscribing to this `/diagnostics` topic will receive\
    \ the raw diagnostics messages (which can be overwhelming on a large system like\
    \ the PR2).\n\nTo visualize raw diagnostics messages in ROS, you can currently\
    \ use the [runtime_monitor](http://ros.org/wiki/runtime_monitor) by simply running:\n\
    \n    rosrun runtime_monitor montior\n\n\n**More Background: The diagnostic_updater**\n\
    \nThe [diagnostic_updater](http://ros.org/wiki/diagnostic_updater) is not quite\
    \ relevant to the aggregator, but is an often-overlooked tool.  It provides convenience\
    \ functions for working with the `DiagnosticArray` messages with your hardware\
    \ drivers in C++.\n\nWith the `diagnostic_updater` libraries, you can create an\
    \ object for interacting with `DiagnosticArray` messgaes, as well as monitoring\
    \ frequency status, and over/under monitoring for critical values in your hardware\
    \ device (temperature, voltage, etc).\n\nThis was mainly included in this write-up\
    \ so that no one tries to reinvent what is already written.\n\n**The Diagnostic\
    \ Aggregator**\n\n[diagnostic_aggregator](http://www.ros.org/wiki/diagnostic_aggregator)\
    \ is a package for aggregating and analyzing diagnostics data.\n\nAssuming that\
    \ you have a working robotic system publishing raw diagnostic data to `/diagnostics`,\
    \ you will see that the raw data accumulates quickly, and becomes cumbersome to\
    \ actually sort through.  For this reason, we use the `diagnostic_aggregator`.\
    \  It allows us to group and sort data into namespaces (much like the ROS computational\
    \ graph).  It will also rate-limit the aggregated diagnostics output to `~pub_rate`\
    \ (typically 1 Hz).\n\nFrom the wiki page, this can transform something like:\n\
    \n    Left Wheel\n    Right Wheel\n    SICK Frequency\n    SICK Temperature\n\
    \    SICK Connection Status\n    Stereo Left Camera\n    Stereo Right Camera\n\
    \    Stereo Analysis\n    Stereo Connection Status\n    Battery 1 Level\n    Battery\
    \ 2 Level\n    Battery 3 Level\n    Battery 4 Level\n    Voltage Status\n\nInto\
    \ something that is more readable, like:\n\n    My Robot/Wheels/Left\n    My Robot/Wheels/Right\n\
    \    My Robot/SICK/Frequency\n    My Robot/SICK/Temperature\n    My Robot/SICK/Connection\
    \ Status\n    My Robot/Stereo/Left Camera\n    My Robot/Stereo/Right Camera\n\
    \    My Robot/Stereo/Analysis\n    My Robot/Stereo/Connection Status\n    My Robot/Power\
    \ System/Battery 1 Level\n    My Robot/Power System/Battery 2 Level\n    My Robot/Power\
    \ System/Battery 3 Level\n    My Robot/Power System/Battery 4 Level\n    My Robot/Power\
    \ System/Voltage Status\n\nAdditionally, each group is given a `level`, which\
    \ allows you to quickly see at-a-glance, where the errors are on your machine.\
    \  ERROR and WARN propagates up the tree.  For instance, an ERROR on `Left` propagates\
    \ up to an ERROR on `Wheels`, and an `ERROR` on My Robot.\n\nThis can then be\
    \ inspected using the [robot_monitor](http://www.ros.org/wiki/robot_monitor) tool.\n\
    \n**Why Should I Use This**\n\nUsing `/diagnostics` is best practice on a robotic\
    \ system of any scale.  It makes troubleshooting hardware (and software) easier\
    \ in almost all cases.\n\nUsing `/diagnostics_agg` is good practice on any larger\
    \ robotic system.  It is also good practice on any sort of production system,\
    \ as it allows more flexibility and clarity when looking at diagnostics data.\n\
    \nAdditionally, if the system is already set up to use aggregated diagnostics,\
    \ the user may choose to write additional analyzer plugins for their system, further\
    \ customizing diagnostic analysis.\n\n**Helpful Resources**\n\n - [diagnostics](http://www.ros.org/wiki/diagnostics)\n\
    \ - [robot_monitor](http://www.ros.org/wiki/robot_monitor)\n - [runtime_monitor](http://www.ros.org/wiki/runtime_monitor)\n\
    \ - [microstrain_3dmgx2_imu](http://www.ros.org/wiki/microstrain_3dmgx2_imu) -\
    \ A node that publishes good diagnostics data\n - [pr2_analyzers.yaml](https://code.ros.org/svn/ros-pkg/stacks/diagnostics/trunk/diagnostic_aggregator/demo/pr2_analyzers.yaml)\
    \ - A good example of setting up analyzers for use with diagnostic_aggregator"
