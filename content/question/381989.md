Dear Awesome people,

**TL;DR: in a pick and place task: want to set the parallel-finger gripper opening value as part of the robot target pose, so it is considered during planning (and therefore collision checking), but while using the final robot pose in Cartesian space.**

I am currently working on a pick and place pipeline, using a 6DOF robot arm with a parallel-finger gripper. Through many iterations of increasing success and speed I realized I could improve the system greatly if I could incorporate the gripper into the robot planning.

The explain myself better: currently, the robot and the gripper controllers are separate, pretty much following [this tutorial](https://github.com/ros-planning/moveit_tutorials/blob/kinetic-devel/doc/controller_configuration/controller_configuration_tutorial.rst) to the letter. Both the arm and the gripper have their own controllers, I can actuate the gripper from the MoveIt! plugin in RViz or programmatically via `GripperAction`. Concurrency is not possible, the actions need to be done sequentially: gripper action, move. gripper action, move…

To set the picking pose I use `move_group.set_pose_target()` which needs a `PoseStamped` message (this is important for later).

Planning is done only for the robot arm joints (as only the link pose is defined via `set_pose_target()`).

To optimize the pick and place pipeline speed I would like to control the *pre-grasp* gripper opening so as to set it to the minimum needed opening so the grasp could be performed quickly. Ideally, this is done while the robot is moving to the target pose as it can be done in parallel to the robot arm joint actuation. That’s where the challenge starts…

Using the previously mentioned *sequential* strategy, the gripper must be in its final *pre-grasp* configuration before the planning is requested, as concurrency is not possible. The reason being that the collision checker only considers the robot joints the planner can actually actuate. Non-controllable joints are assumed static.

This has two undesirable consequences:

1. It does not fulfill my requirement of wanting to speed up the picking process.
2. When there are adjacent/bulk objects, the collision check is done with the gripper being open. Often this is not ideal: a slightly closed gripper might be able to avoid colliding with adjacent objects.

Currently, I set the gripper opening and then call the planner. This works well and is probably as the original design wanted it: it allows robot and end-effector abstraction. It looks elegant and works as expected.

Now comes the real reason for all of this: there are multiple grasping poses provided, along with their respective optimal gripper opening values. The first pose/opening combo to pass the planning stage can be attempted, this planning is very fast (a fraction of a second), but having to set the gripper opening before the planning can be requested defeats this strategy as it can take more than a second to actuate the gripper.

A faster approach would be to set all the target joint poses, including the gripper joints, and only then request the planning: the gripper joints would be part of the planning and the collision checker could test the actuated gripper configuration, instead of only the initial one.

Now, back to the beginning: I said I use the `move_group.set_pose_target()` function to set the robot target joint poses indirectly in the Cartesian space. Unfortunately, this does not allow me to set the gripper opening, as it only takes the goal `PoseStamped` message, defined for the requested link name.

The only other function I know, that could help, would be `set_joint_value_target()`. If I had a proper hardware interface for the gripper I could probably set all joint values this way, including the gripper, but then I have no clue how to get the target robot joint values as it requires IK…

Maybe there is different, more elegant, strategy to what I want to do: set the pre-grasp gripper opening as part of the planning, so the collision checker would consider it.

[This question](https://answers.ros.org/question/198706/how-to-plan-moves-with-gripper-attached-to-arm/) was similar, but did not develop the method I wanted to use.
