  body_markdown: "There are two modes that future callbacks are called. Either they're\
    \ called directly by the future, or they're scheduled with an executor. It's up\
    \ to the executor to decide what order to call them in.\n\nThis example creates\
    \ a future without an executor.\n\n    from functools import partial\n    from\
    \ rclpy.task import Future\n    \n    def callback(name, future):\n        print(f\"\
    I am callback {name}\")\n    \n    f = Future()\n    f.add_done_callback(partial(callback,\
    \ 'alice'))\n    f.add_done_callback(partial(callback, 'bob'))\n    f.add_done_callback(partial(callback,\
    \ 'charlie'))\n    f.set_result(\"foobar\")\n\nIt calls done callbacks in the\
    \ order they're added\n\n    I am callback alice\n    I am callback bob\n    I\
    \ am callback charlie\n\nThis future [schedules callbacks with a SingleThreadedExecutor]().\n\
    \n    import rclpy\n    from rclpy.executors import SingleThreadedExecutor\n \
    \   \n    rclpy.init()\n    s = SingleThreadedExecutor()\n    f = Future(executor=s)\n\
    \    \n    f.add_done_callback(partial(callback, 'amy'))\n    f.add_done_callback(partial(callback,\
    \ 'brice'))\n    f.add_done_callback(partial(callback, 'cole'))\n    f.set_result(\"\
    foobar\")\n    \n    s.spin_once()\n    s.spin_once()\n    s.spin_once()\n   \
    \ s.spin_once()\n    \n    rclpy.shutdown()\n\nIt happens to call them in reverse.\n\
    \n    I am callback cole\n    I am callback brice\n    I am callback amy\n\nThey're\
    \ reversed because [the executor checks which tasks are ready in reverse](https://github.com/ros2/rclpy/blob/22816b41f66bcdb20adcca0b92fb7c8149710297/rclpy/rclpy/executors.py#L478-L483).\
    \ Reversing the order means if an old task has `yield`'d or `await`'d because\
    \ it's waiting for something to happen, then a new task ([appended to the end\
    \ of the task list](https://github.com/ros2/rclpy/blob/22816b41f66bcdb20adcca0b92fb7c8149710297/rclpy/rclpy/executors.py#L199))\
    \ gets to run first and potentially unblock the old task.\n\nThat doesn't mean\
    \ an executor is guaranteed to execute the tasks in reverse though. The order\
    \ of callbacks in a Multithreaded executor depends on the order the operating\
    \ system schedules threads.\n\n    import rclpy\n    from rclpy.executors import\
    \ MultiThreadedExecutor\n    \n    rclpy.init()\n    s = MultiThreadedExecutor()\n\
    \    f = Future(executor=s)\n    \n    for i in range(100):\n        f.add_done_callback(partial(callback,\
    \ i))\n        f.set_result(\"foobar\")\n    \n    for i in range(100):\n    \
    \    s.spin_once()\n    \n    rclpy.shutdown()\n\nIt tends towards reverse order\
    \ but is still pretty random\n\n    ...\n    I am callback 95\n    I am callback\
    \ 93\n    I am callback 92\n    I am callback 94\n    I am callback 89\n    I\
    \ am callback 88\n    I am callback 90\n    ...\n\n"

title: Why is the Future 'done callback' order reversed?
upvote_count: 1

I'd like to attach multiple callbacks to a `Future` provided by a `ClientGoalHandle`. However, when I do this I find that the callbacks are being called in reverse order. I'm a little stumped as to why this is happening. When I look through the code for `rclpy.executor` or `rclpy.task` I can only see `for callback in callbacks`.

Here's a snippet from my code:

    @property
    def logger(self):
        return self._node.get_logger()

    def foo(self, *args, **kwargs):
        self.logger.info('foo')

    def bar(self, *args, **kwargs):
        self.logger.info('bar')

    def baz(self, *args, **kwargs):
        self.logger.info('baz')

    def qux(self, *args, **kwargs):
        self.logger.info('qux')

    def next(self) -> Optional[Future]:
        self._clear_cache()
        if self.goal_handle is not None:
            self.logger.info("Cancelling current guidance.")
            future = self.goal_handle.cancel_goal_async()
            future.add_done_callback(self.foo)
            future.add_done_callback(self.bar)

            self._goal_future.add_done_callback(self.baz)
            self._goal_future.add_done_callback(self.qux)

            return self._goal_future
        else:
            return None

Here is the console readout in which you can see `bar` is called before `foo` and `qux` is called before `baz`:

I can 'fix' this by reversing the future callback order:

    with future._lock:
        future._callbacks.reverse()

But it feels like a hack to mess around with private variables within the future class. Any ideas?
