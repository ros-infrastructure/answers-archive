  body_markdown: "There are several possible reasons for the symptoms you describe:\n\
    \n- At least one of the required Gazebo plugins has not been loaded for some reason\
    \ or could not parse its parameters from the URDF description. You should check\
    \ the console output if there are error messages that could serve as a starting\
    \ point. Also check that `/cmd_vel` is published correctly using `rostopic echo\
    \ /cmd_vel` and that gazebo subscribes to this topic `rostopic info /cmd_vel`.\n\
    \n- There might be NaN values for some reason in a message the controller plugin\
    \ uses to calculate the required thrust and torques. You can check this easily\
    \ with `rostopic echo`. Using the default configuration, the relevant topics are\
    \ `/ground_truth/state` and `/raw_imu`.\n (*Note:* There was a bug introduced\
    \ in revision 811 and resolved in revision 814 that caused the IMU plugin in [hector_gazebo_plugins](http://ros.org/wiki/hector_gazebo_plugins)\
    \ to publish NaN values for the first timestep, which are fed through to the torque\
    \ output due to the integrators in the controller.)\n\n- Make sure to NOT use\
    \ the propulsion model plugin in package [hector_quadrotor_controller](http://ros.org/wiki/hector_quadrotor_controller)\
    \ as for now. This plugin requires an installation of Matlab with Matlab Coder\
    \ to compile successfully, and when the binary is found, the cmake scripts in\
    \ [hector_quadrotor_gazebo](http://ros.org/wiki/hector_quadrotor_gazebo) will\
    \ add it to the quadrotor URDF instead of the simple controller plugin. The propulsion\
    \ plugin requires motor voltages as input and does not react on `/cmd_vel` directly.\
    \ We bridge this gap by running our onboard software running in [Orocos RTT](http://ros.org/wiki/orocos_toolchain)\
    \ with [ROS integration](http://ros.org/wiki/rtt_rosnode), which is not (yet)\
    \ available in the repo. When the propulsion model is enabled without a running\
    \ controller, the quadrotor will just fall down and stay on the ground. Without\
    \ the plugin it is not really possible to touch down, as the simple controller\
    \ will always produce a certain thrust required to compensate gravity. When no\
    \ commands are received, the quadrotor will hover a couple of centimeters above\
    \ ground and slowly [drifts away](http://answers.ros.org/question/37080/simulated-quadrotor-is-slowly-drifting-on-its-own/)\
    \ due to IMU noise and numerical inaccuracies.\n \n You can disable the propulsion\
    \ plugin with the command\n <pre>\n roscd hector_quadrotor_gazebo/build && cmake\
    \ . -DUSE_PROPULSION_MODEL=OFF\n </pre>\n\n- If you are using ROS fuerte, you\
    \ should first try to install hector_quadrotor from the package repository instead\
    \ of doing a source installation:\n <pre>\n sudo apt-get install ros-fuerte-hector-quadrotor\n\
    \ </pre>\n \n We expect to release a new version of the stack for fuerte and groovy\
    \ as soon as [some problems](http://answers.gazebosim.org/questions/scope:all/sort:activity-desc/query:groovy/page:1/)\
    \ with the new Gazebo version (e.g. spawning at the wrong position) have been\
    \ resolved.\n\n When checking out the SVN version directly, make sure to use the\
    \ [/trunk](https://tu-darmstadt-ros-pkg.googlecode.com/svn/trunk/hector_quadrotor)\
    \ version to also get the latest updates. Unfortunately the wiki page is still\
    \ showing an outdated URL in /branches/fuerte for ROS fuerte (see [this question](http://answers.ros.org/question/53658/which-repository-url-is-displayed-in-the-ros-wiki/))."
