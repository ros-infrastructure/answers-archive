  body_markdown: "**Subscriber Counter Throttle**\n\nKeep a counter in the callback\
    \ that returns without doing anything unless `counter % 50 == 0`- but there is\
    \ a deserialization performance hit involved there\n\n**Standard Throttle**\n\n\
    The topic_tools throttle should not have the deserialization penalty depending\
    \ on how [ShapeShifter](https://github.com/ros/ros_comm/blob/lunar-devel/tools/topic_tools/src/throttle.cpp)\
    \ works.   \n\n**Nodelet Throttle**\n\nA nodelet version of throttle would be\
    \ nice to eliminate additional copies between throttle and your subscriber- and\
    \ it turns out it already exists: http://wiki.ros.org/nodelet_topic_tools (is\
    \ there any reason why there should be a non-nodelet version of throttle that\
    \ isn't just a wrapper around the nodelet?).  You would have to make your subscriber\
    \ a nodelet and put it into the same nodelet manager as the throttle.  Copying\
    \ 50 messages a second is not a big proportion of the cpu being compared to the\
    \ resources required for handling the other 950 messages, so maybe the nodelet\
    \ isn't worth the trouble.\n\nAdditionally, in [looking at the code for this nodelet\
    \ throttle](https://github.com/ros/nodelet_core/blob/indigo-devel/nodelet_topic_tools/include/nodelet_topic_tools/nodelet_throttle.h)\
    \ it appears to be using a template system rather than the generic ShapeShifter\
    \ message that the regular throttle uses, which means it is deseerializing and\
    \ reserializing everything, making it slower than regular throttle as the test\
    \ result below shows.\n\nThe template system also requires you to create your\
    \ own nodelet that instantiates the type you want to throttle, which is non-trivial,\
    \ but [there is an Image example](https://github.com/jon-weisz/camera_throttler_nodelets)\
    \ and I've made an [imu nodelet throttle](https://github.com/lucasw/topic_throttle/blob/master/test/imu_nodelet_throttle.cpp).\n\
    \n**Queue Throttling**\n\nA different and hacky approach is to keep track of time\
    \ since the last processed subscribed message in your callback, and do a blocking\
    \ sleep with the remaining 1/50th of a second while also having a  subscriber\
    \ queue_size of 1. \n\n> If the queue is full and a new message\n> arrives, the\
    \ oldest message will be\n> thrown out. Additionally, the message\n> is not actually\
    \ deserialized until the\n> first callback which needs it is about\n> to be called.\n\
    \nhttp://wiki.ros.org/roscpp/Overview/Publishers%20and%20Subscribers#Queueing_and_Lazy_Deserialization\n\
    \n**Test Results**\n\n- A python node publishing Imu at 1000 Hz takes about 14%\
    \ cpu.\n- regular throttle takes about 7% cpu\n- nodelet throttle (in a wrapper)\
    \ takes 10% cpu\n- [Queue overflow method with rospy node](https://github.com/lucasw/topic_throttle/blob/master/scripts/imu_sub.py)\
    \ takes 2% cpu, though the queue isn't getting updated properly.\n- [Queue overflow\
    \ with cpp node](https://github.com/lucasw/topic_throttle/blob/master/src/queue_throttle.cpp)\
    \ takes 5% cpu and timing seems solid\n- The python node subscribing to Imu (and\
    \ doing nothing with it) at the throttled 50 hz is negligible.\n- Python imu subscriber\
    \ without throttling takes 8% cpu\n- C++ imu subscriber without throttling takes\
    \ 7% cpu \n\nOne unexpected result is that a python subscriber plus regular throttle\
    \ doesn't run any faster than a python or C++ node subscribing to the full rate\
    \ Imu topic.\n\nThe rospy queue throttling node got increasingly behind with the\
    \ messages it was receiving, while the C++ version worked fine and so far is the\
    \ best solution for the most efficient throttle.\n\nAll the code is on https://github.com/lucasw/topic_throttle"
