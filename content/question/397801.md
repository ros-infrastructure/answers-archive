[Working in ROS noetic ubuntu 20.04]
I've a topic publishing robot joints at 100 Hz and the following code for testing purposes:

    from sensor_msgs.msg import JointState
    import rospy
    
    rospy.init_node("queue_size_testing", anonymous=True)
    
    def callback(msg) -> None:
        now = rospy.Time.now()
        print(f"[ACTUAL] secs={now.secs} nsecs={now.nsecs} [READ]secs={msg.header.stamp.secs} nsecs={msg.header.stamp.nsecs}")
        rospy.sleep(0.1)
    
    rospy.Subscriber('/joint_states',JointState,callback)
    rospy.spin()

I'm just subscribing to the topic and executing the callback at 10 Hz (obviously this code is not appropriate since it makes no sense to make the callback sleep, it is developed for testing purposes). So, this code is able to process 10 messages per second, even if 100 are coming from the publisher.
As I have not defined a value for the subscriber's queue_size, it has taken its default value (infinite).

Summarizing I've tested 4 setups, publishing from a 100 Hz topic:

 - Callback at 10 Hz with infinite queue_size in the subscriber with unexpected behavior as it seems like the FIFO behavior is lost. It seems like a strange race condition is appearing, the msgs are publishing in pairs.
 - Callback at 10 Hz with queue_size=1 in the subscriber with a more understandable behavior (still a bit unexpected as the receiving times seems to be deterministic but 2 of them are present), still a race condition appears to be present as they're published in pairs.
 - Callback as fast as possible with infinite queue_size in the subscriber with expected behavior, for the same time in the callback multiple readings are processed, but this is reasonable as the callback calling dispatcher is faster due to having more msgs de-serialized at a time.
 - Callback as fast as possible with queue_size=1 in the subscriber with expected behavior.
