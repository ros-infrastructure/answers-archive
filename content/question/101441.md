    CMake itself does support specifying versions of packages (see [cmake.html#find_package](http://www.cmake.org/cmake/help/v2.8.11/cmake.html#command:find_package)), but only if the `FindX.cmake` script implements it. AFAIK many of the find scripts provided with the binary CMake distribution do.

    <s>I may be wrong, but Catkin does not seem to (currently) expose this in its `catkin_package(..)` macro AFAICT (see [groovy-devel/cmake/catkin_package.cmake](https://github.com/ros/catkin/blob/groovy-devel/cmake/catkin_package.cmake)). There is some version checking going on in [groovy-devel/cmake/catkin_package.cmake](https://github.com/ros/catkin/blob/groovy-devel/cmake/catkin_package.cmake#L188) around line 188, but I can't tell from the source how that should work.</s> See edit.

    As for detecting support for features vs relying on version numbers: that approach would seem superiour, and is the one that's been advocated by the javascript / browser-based application developer community for a long time now. Plain CMake may be able to help you with this, see [cmake.html#CheckFunctionExists](http://www.cmake.org/cmake/help/v2.8.11/cmake.html#module:CheckFunctionExists).

    ---

    Edit: according to [REP-127](https://github.com/ros-infrastructure/rep/blob/master/rep-0127.rst), it is possible to specificy versioned dependencies (from the [example](https://github.com/ros-infrastructure/rep/blob/master/rep-0127.rst#example) in that REP):

        <build_depend version_gte="1.1" version_lt="2.0">genmsg</build_depend>

    I assume this information is then passed to the version checking in [groovy-devel/cmake/catkin_package.cmake](https://github.com/ros/catkin/blob/groovy-devel/cmake/catkin_package.cmake#L188).

The idea would be to pass dependency version information through as a flag and conditionally compile different code paths.

The specific scenario is having packages which depend on a package which I'm in the process of pushing several upstream changes to. In my local workspace, I'd like to build the package against my version of the dependency, but still have it build correctly on the buildfarm against the dependency's upstream (and then ideally switch over to the new code path when upstream merges my changes).

A perhaps better alternative would be using SFINAE tricks to detect if the specific methods I want to take advantage of are present in the class.

Is there an official recommendation for this type of situation?
