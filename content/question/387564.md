    TF between `t265_odom_frame` and `t265_pose_frame` would be published by T265 node, maybe odometry is lost? 600 ms is quite long, if odometry is indeed published (check the corresponding topic `sample`), the timestamps between T265 and timestamps coming from D400 cameras may not be synchronized. I think there are global time options for realsense driver to use computer time instead of sensor time. Maybe it could help to get synchronized stamps between the cameras. One way to debug clock syncrhonization is to `rostopic echo` the header of a T265 topic and the header of a D400 topic in two terminals and look if there is a big difference.

    Similar issue: https://github.com/IntelRealSense/realsense-ros/issues/1906

    \ me: https://answers.ros.org/question/164216/tf-cant-look-up-transform/ & https://answers.ros.org/question/10409/how-to-access-old-transforms-tf/\
    \ \n\nThe main problem was not with my implementation but the fact that rtabmap\
    \ started late and tfListener has a default buffer size of 10.0 secs and after\
    \ 10.0 secs the TF messages are lost while The corresponding earlier D400 messages\
    \ and /t265/odom/sample messages were still available, This caused rtabmap to\
    \ request a TF transformation that is already forgotten by the TransformListener\
    \ and hence the error, so I increased the Buffer size to 60.0 secs and it worked!\n\
    \nThis Buffer size can be increased in  \"tf::TransformListener tfListener_;\"\
    \ object creation in rtabmap_ros/include/rtabmap_ros/OdometryROS.h according to\
    \ the constructor definition found here: https://docs.ros.org/en/api/tf/html/c++/classtf_1_1TransformListener.html#ab3983f7a11656f37d2f7ee0e9da5fe0a\
    \ or you can change the default value (const double tf::Transformer::DEFAULT_CACHE_TIME)\
    \ in tf/src/tf.cpp"
