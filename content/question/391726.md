    You are describing a systemd behavior, not a ros issue. <del>By removing the ".local" from the hostname, you've probably excluded those machines from using Multicast DNS.</del> By default, systemd is going to form a FQDN using the hostname + subnet name provided by the DHCP server.

    I have never needed to use multicast DNS, but have you tried creating hostname aliases in /etc/hosts on both hosts? Or maybe see if avahi-daemon can be configured to opt-in your two specific machines?

    Update: look at this man page: `man avahi-daemon.conf

    Update 2: from what I'm reading, you locally configure the host's name without any subnet name, but you need to access the host using the FQDN `<hostname>.local`. The MDNS guides are not indicating that avahi-daemon.conf needs to be modified for this situation.

    Since the rabbit hole of investigating existing known working ros packages was leading me definitely in the wrong direction and also because Mike seemed so adamant that ros could not be at fault, thanks Mike, I decided to compare in detail the entire home folder from both robots. This showed my mistake when looking at the .bashrc files.<br>

    Melodic .bashrc:<br>

    ROS_MASTER_URI=http://rosbot.local:11311<br>
    ROS_HOSTNAME=rosbot.local<br>

    Kinetic .bashrc:<br>

    export ROS_MASTER_URI=http://rosbot.local:11311<br>
    export ROS_HOSTNAME=rosbot.local<br>

    As can be seen the 'export' command was missing!!!<br>
    Case closed

As my first post, I apologise if this question has been asked before, it is just that my searches here and with google pointed at the site:answers.ros.org did not reveal any insight into my challenge.

OVERVIEW<br>
In both scenarios I use a ROS Master (robot), and a ROS Client/Slave (Laptop)<br>
WiFi network provides DHCP on router without DNS registration or DNS services<br>
I have also tried static IP's on both with a cable directly between both robot and laptop and get same error<br>
No firewalls on either versions of Ubuntu<br>
Multicast DNS is what is relied upon using avahi-daemon in default config<br>
For the purpose of this question the FQDN of Robot and Laptop are as below:<br>
Robot FQDN:   **rosbot.local**         Robot hostname:  **rosbot**<br>
Laptop FQDN:  **laptop.local**         Laptop hostname: **laptop**

Robot **.bashrc** entries:<br>
ROS_MASTER_URI=http://**rosbot.local**:11311<br>
ROS_HOSTNAME=**rosbot.local**<br>

Laptop **.bashrc** entries:<br>
ROS_MASTER_URI=http://**rosbot.local**:11311<br>
ROS_HOSTNAME=**laptop.local**

WORKING ROBOT<br>
In the Kinetic/Ubuntu 16.04 scenario all is working fine<br>
On Robot I launch roscore and on the Laptop I run roswtf, rviz, rqt graph all work fine and as expected<br>
Network validation checks have been completed as per http://wiki.ros.org/ROS/NetworkSetup

NOT WORKING ROBOT<br>
In the Melodic/Ubuntu 18.04 scenario, it seems hostname and NOT FQDN is now the preferred choice for the likes of roswtf, rviz, and rqt graph<br>
Network validation checks have once again been completed as before<br>
As per Kinetic, I launch roscore and on laptop I run roswtf and get the following error message:<br>
running graph rules...<br>
ERROR: Unknown host [**rosbot**] for node [/rosout]<br>
... done running graph rules

ERROR Errors connecting to the following services:<br>
 * service [/rosout/set_logger_level] appears to be malfunctioning: Unable to communicate with service [/rosout/set_logger_level], address [rosrpc://**rosbot**:53773]<br>
 * service [/rosout/get_loggers] appears to be malfunctioning: Unable to communicate with service [/rosout/get_loggers], address [rosrpc://**rosbot**:53773]

Launching rviz and rqt_graph also not working

During this testing, I did the following as a temporary fix and this proved my suspicion about hostname and NOT FQDN being used in Melodic:<br>
I added a host IP entry for the name rosbot into the /etc/hosts file of the laptop<br>
After doing this roswtf, rviz, and rqt graph all work again<br>
Unfortunately in a dynamic IP environment, writing a script workaround on the laptop to do this every time the robot gets a new IP is not the preferred direction I would like to take.

Something has obviously changed between Kinetic and Melodic, and any assistance in identifying what it is and some direction I can take from here would really be appreciated.<br>
