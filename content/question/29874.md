  body_markdown: "A quick summary, and then on to code samples:\n\n 1. Build your\
    \ driver node to be completely ROS-agnostic.  In your class, define a series of\
    \ (private) function pointers to logging functions for you different levels, Debug,\
    \ Info, Error, etc.\n 2. In your class, define a few \"setters\" to update these\
    \ function pointers.\n 3. In your class, create some generic loggers (or use the\
    \ logging system of your choice), and make these default in the constructor\n\
    \ 4. In your node, create some wrappers to the ROS functions.\n 5. When constructing\
    \ the driver object, make sure to also update the logging function pointers to\
    \ your new ROS function pointers.\n\n**C++**\n\nI think a decent example of this\
    \ is @wjwwood's libsegwayrmp library.\n\nTo begin with, he typedef's a few functions:\n\
    \n    typedef boost::function<void(const std::string&)> DebugMsgCallback;\n  \
    \  typedef boost::function<void(const std::string&)> InfoMsgCallback;\n    typedef\
    \ boost::function<void(const std::string&)> ErrorMsgCallback;\n\nAnd then creates\
    \ private class variables in his hardware driver;\n\n    ...\n    private:\n \
    \      DebugMsgCallback debug;\n       InfoMsgCallback info;\n       ErrorMsgCallback\
    \ error;\n\nAnd he creates three public mutators to update these function pointers:\n\
    \n    void setErrorMsgCallback(ErrorMsgCallback);\n    void setInfoMsgCallback(InfoMsgCallback);\n\
    \    void setDebugMsgCallback(DebugMsgCallback);\n\nThe logging functions can\
    \ be called in your class by simply doing:\n\n    this->error(\"This is an error\
    \ message\")\n    this->debug(\"This is a debug message\")\n    this->info(\"\
    This is an info message\")\n\nSo now, to use this WITHOUT ROS, you can create\
    \ three simple callback functions that just log to the console, or modify these\
    \ for your own logging suite:\n\n    inline void defaultDebugMsgCallback(const\
    \ std::string &msg) {\n        std::cerr << \"SegwayRMP Debug: \" << msg << std::endl;\n\
    \    }\n    \n    inline void defaultInfoMsgCallback(const std::string &msg) {\n\
    \        std::cerr << \"SegwayRMP Info: \" << msg << std::endl;\n    }\n    \n\
    \    inline void defaultErrorMsgCallback(const std::string &msg) {\n        std::cerr\
    \ << \"SegwayRMP Error: \" << msg << std::endl;\n    }\n\nOr, to use it WITH ROS,\
    \ you can create some functions that wrap the macros:\n\n    void handleDebugMessages(const\
    \ std::string &msg) {ROS_DEBUG(\"%s\",msg.c_str());}\n    void handleInfoMessages(const\
    \ std::string &msg) {ROS_INFO(\"%s\",msg.c_str());}\n    void handleErrorMessages(const\
    \ std::string &msg) {ROS_ERROR(\"%s\",msg.c_str());}\n\nWhen you construct the\
    \ device driver, you can then update these function pointers to your newly-wrapped\
    \ functions:\n\n    this->segway_rmp->setDebugMsgCallback(handleDebugMessages);\n\
    \    this->segway_rmp->setInfoMsgCallback(handleInfoMessages);\n    this->segway_rmp->setErrorMsgCallback(handleErrorMessages);\n\
    \n**Python**\n\nYou do a similar thing with Python.  I create my hardware interfaces\
    \ to use the default Python `logging` built-in.  The signature for these functions\
    \ is:\n\n    f(msg, *args)\n\nWhich happens to be the same as the ROS logging\
    \ system.\n\nUsing a similar strategy, I create a few function references as class\
    \ variables:\n\n    class DriverObject(object):\n        def __init__(self, param1,\
    \ param2, param3, debug=None, info=None, error=None):\n            self.debug\
    \ = logging.debug                                                   \n       \
    \     self.info = logging.info                                               \
    \      \n            self.error = logging.error                              \
    \                                                                            \
    \                               \n            if debug:                      \
    \                                              \n                self.debug =\
    \ debug                                                       \n            if\
    \ error:                                                                    \n\
    \                self.error = error                                          \
    \             \n            if info:                                         \
    \                            \n                self.info = info\n\nAnd to use\
    \ these functions throughout my class, I simply do:\n\n    self.debug(\"This is\
    \ a debug message\")\n    self.error(\"This is an error message\"\n    self.info(\"\
    This is an info message\")\n\nAnd when I want to use the class within a ROS node:\n\
    \n    import rospy\n    from driver import DriverObject\n    \n    do = DriverObject(1,1,1,debug=rospy.logdebug,\
    \ info=rospy.loginfo, error=rospy.logerr)\n\nAnd now all the logging goes through\
    \ the ROS logging system."

    \ the logs are automatically published on `/rosout`\n - The logging namespace\

  body_markdown: "I ran into similar issues.  The ROS logging macros are numerous\
    \ and defined 5 or more levels deep, so whenever you pass the wrong one of the\
    \ plethora of stringy types in C++, you get several screenfulls of preprocessor\
    \ error. \n\nIf you're developing in C++11, you can use closures to bring back\
    \ a measure of explicitly typed sanity:\n\n        auto log_info =  [] (const\
    \ std::string & str) {ROS_INFO_STREAM(str);};\n        auto log_warning =  []\
    \ (const std::string & str) {ROS_WARNING_STREAM(str);};\n        auto log_error\
    \ =  [] (const std::string & str) {ROS_ERROR_STREAM(str);};\n\nThere are probably\
    \ many ways of defining the above closures; there may be a better one for your\
    \ code.  Doing it this way decomposes the task of fixing the types in the call\
    \ sites in your code from the much harder problem of figuring out which types\
    \ will actually work in ROS's macros.  \n\nI'm sure there are reasonable historical\
    \ reasons for why ROS is code generating header files full of macros nested 5\
    \  levels deep, but IMHO it has resulted in an unreasonable level of complexity\
    \ for something as simple as logging a string.  Perhaps someone can post an example\
    \ of what all the macros actually boil down to in the end."

I'm writing two new classes:

 - A class that controls a motor control board (mcb)
 - A ROS node that contains an object of the mcb class. This node provides services to the rest of ROS that use the mcb.

The mcb class will be used later on in non-ROS applications and needs to be stand alone.  That's not hard to do, but since I'm using ROS now I'd like to use the nice ROS_[INFO|ERROR] logging functionality.

My idea was to have a logfunction function pointer in the mcb class that the caller could supply. That would give the caller the opportunity to print statements to standard output by supplying printf, to log to ROS with the ROS log stuff, or to log some other way by a custom function.

The only problem is that ROS_[INFO|ERROR|etc.] are all macros, and can't be pointed to as far as I know.  I also can't wrap the logging macros in functions, because it's not possible to pass ellipses, right?

Does anybody know of a way to provide the logging functionality through a pointer or a stream or something? Or is there any way to put outside log messages into the ROS logging system?
