    \ especially when it comes to installing from source.\n\nThis is my personal experience,\
    \ and I had limited iterations with it (tried just a few times) but worked well.\n\
    \nStart with a standard debian SD image;  Run this image using QEMU, on a regular\
    \ (powerful) computer.\n\nBefore you start, make sure you have enough space on\
    \ that image. Two GB can be too small. Four GB just right for the basics. I would\
    \ recommend 16 GB, if the price is right for you. Keep in mind that later you\
    \ will install this image on an ACTUAL SD card.\n\nInstead of creating an image\
    \ with 16 GB, create it with 15900 MB. It is the never ending discussion about\
    \ 1024 vs 1000, and sometimes the actual available space on a storage device will\
    \ not be the ACTUAL reported space on the label.\n\n There are a few tricks you\
    \ have to apply in order to get your ARM image to run on a qemu environment, but\
    \ it works well. download, install and compile all you want on that image \n\n\
    I no longer have the links that I used to create my images, but here are the key\
    \ points:\n\n- resizing an SD image (tricky. Look into solutions that include\
    \ gparted, and mounting the image as a loop device).\n- Running the image with\
    \ quemu (relatively easy, but you will be \"limited\" to 256 MB ram)\n- transferring\
    \ the final image to the SD card.\n\nNote: I did it for Hydro. Not yet for Indigo,\
    \ but it should work.\n\nCheers.\n\n\n\n\n++++++++++++++++++++++++-----------\
    \  LONG ADDITION -------------+++++\n\nWell, would you look at that. I found some\

    \ my first steps in the ROS world, and my weapons of choice are a Raspberry PI\
    \ (rev b, with 512 MB), an Ubuntu 12.04 running on VMWare Fusion, to be used as\
    \ the \"base station\", and an idea in my head.\n\nAnyone trying their luck with\
    \ a RPI knows that installing ROS takes time. Some brave souls out there created\
    \ images for SD card with ROS already installed, and that is a brilliant job they've\
    \ done.\n\nI had problems with those images, so I had to start my own tests.\n\
    \nNow, the very first obstacle was the processing power of the RPI, so, like many,\
    \ I decided to go virtual, using QEMU to install and compile everything. \n\n\
    The other \"little problem\"  I ran into was, the default Debian Wheezy image\
    \ I was using was not even 4 GB, with very little space available.\n\nMaking a\
    \ mistake on the ROS install, or messing up with the operation system could render\
    \ an entire week of work useless.\n\nVirtualizing would allow me to:\n\n1) Take\
    \ advantage of an i7 processor to install ROS\n2) Make intermediated copies of\
    \ the image, whenever I thought a \" dangerous\" step in the install was ahead.\n\
    3) Take the environment with me (notebook) wherever I was\n4) Manage image space\
    \ as required, instead of just using a big 16 GB SD card. This makes a lot of\
    \ difference when creating images and buying test SD cards, not to mention time\
    \ to record those images and test them on the RPI.\n\nBut, resizing the image\
    \ proved to be trickier than I thought; There are many tutorials and howtos out\
    \ there, but few have the goal of resizing an image, using it on a virtual environment,\
    \ and next recording it to be used back on the actual thing.\n\nMy work here was\
    \ based on these pages:\n\nResizing img file:\n\nhttp://sirlagz.net/2012/06/20/how-to-resize-partitions-on-an-image-file/\n\
    \nQEMU RPI emulation:\n\nhttp://xecdesign.com/qemu-emulating-raspberry-pi-the-easy-way/\n\
    \n\nInstalling ROS:\n\nhttp://wiki.ros.org/ROSberryPi/Setting%20up%20Hydro%20on%20RaspberryPi\n\
    \n\n--------------\n\nWhat first ?\n\nDo NOT boot your image. Do everything with\
    \ exclusive access to the img file. Make a backup copy just in case. \n\nI started\
    \ with the latest Raspbian image, instead of NOOB. Should not make any difference\
    \ for ROS or Linux, but might do for disk resizing. Be careful.\n\nNow, just out\
    \ of curiosity, running fdisk -l on my wheezy's image showed a FAT partition and\
    \ an EXT4 partition. Contrary to many tutorials out there, a swap partition was\
    \ not found and this is important, because you don't have to move that swap partition.\n\
    \nNow, a word of advice here: in one step you will DELETE you actual partition\
    \ information. If you do it right, no data will be lost. Fear not, but make sure\
    \ you know what you are doing.\n\nThese instructions offer no danger to your hard\
    \ drive, for they do not use DD, but then again: your system, your responsibility.\
    \ \n\n\n---------------  Resize wheezy partition\n\nYou are on Ubuntu's terminal.\n\
    \nFirst, we have to create extra space on the image file. Do it easily with qemu-image,\
    \ and replace the \"1G\" with the amount of space you want to ADD to the image.\n\
    \nIn my case my image is called alpha1_wRh.img\n\n\nqemu-img resize alpha1_wRh.img\
    \ +1G\n\n\nThis is ready in a split second. Next, we mount the image as a loopback\
    \ device in order to have some access to it.\n\nlosetup -f --show \n\nAnd now\
    \ enter gparted to make the important changes:\n\ngparted alpha1_wRh.img \n\n\
    You will see the usual prompt on parted, and will use the \"print\" command, which\
    \ will tell you more or less this:\n\n(parted) print\nModel:  (file)\nDisk alpha1_wRh.img:\
    \ 3996MB\nSector size (logical/physical): 512B/512B\nPartition Table: msdos\n\n\
    Number  Start   End     Size    Type     File system  Flags\n 1      4194kB  62.9MB\
    \  58.7MB  primary  fat16        lba\n 2      62.9MB  2962MB  2899MB  primary\
    \  ext4\n\nNow comes the horrible part that is the nightmare of us all: delete\
    \ that partition number 2.\n\nrm 2\n\nand next, create it again with \n\nmkpart\
    \ primary 62.9 3996\n\nNow, where have I got the magic numbers from above? 62.9\
    \ is the start of the original partition, and 3996 is the \"disk\" size reported\
    \ by parted, on the second line to the \"print\" command. \n\nAfter this, enter\
    \ \"quit\" to exit parted, committing the changes.\n\n\nNow, we are getting there,\
    \ but we have to use some more \"magic\" and the real voodoo is yet to come.\n\
    \nRun this command on you just altered file:\n\nfdisk -l alpha1_wRh.img\n\nIts\
    \ output should look like this:\n\n\nDisk alpha1_wRh.img: 2962 MB, 2962227200\
    \ bytes\n255 heads, 63 sectors/track, 360 cylinders, total 5785600 sectors\nUnits\
    \ = sectors of 1 * 512 = 512 bytes\nSector size (logical/physical): 512 bytes\
    \ / 512 bytes\nI/O size (minimum/optimal): 512 bytes / 512 bytes\nDisk identifier:\
    \ 0x000981cb\n\n         Device Boot      Start         End      Blocks   Id \
    \ System\nalpha1_wRh.img1            8192      122879       57344    c  W95 FAT32\
    \ (LBA)\nalpha1_wRh.img2          122880     5785599     2831360   83  Linux\n\
    \nThere are some very interesting points here: \n\na) The \"sector size\" is 512.\
    \ Take note of this number.\nb) The \"Start position\"  of you Linux partition\
    \ is 122880. Take note of this too.\n\nMultiply \"sector size\" by \"start point\"\
    \ and use it in the next command. My result is 62914560.\n\nlosetup -f --show\
    \ -o 62914560 alpha1_wRh.img\n\nThis will create a loop device on you system,\
    \ referring to that PART (partition) on your img file, and will return which device\
    \ name was issued. For me it was /dev/loop0\n\nNext is the easy part:\n\nWe test\
    \ the fie system, just in case:\n\ne2fsck -f /dev/loop0\n\nWe resize the file\
    \ system:\n\nresize2fs /dev/loop0\n\nWe check it again, because we want to be\
    \ safe:\n\ne2fsck -f /dev/loop\n\nAnd we no longer need the device, so we delete\
    \ it.\n\nlosetup -d /dev/loop0\n\nDone ! Now you are ready to boot your virtual\
    \ RPI with your bigger disk ! \n\n\n\n\n=====================================================\n\
    Notes for QEMU\n\nqemu commands below are incomplete and must refer to your image\
    \ file.\n\nPreparing your image with bash\n\nqemu-system-arm -kernel kernel-qemu\
    \ -cpu arm1176 -m 256 -M versatilepb -no-reboot -serial stdio -append \"root=/dev/sda2\
    \ panic=1 rootfstype=ext4 rw init=/bin/bash\" -hda\n\n\nRegular boot\n\nqemu-system-arm\
    \ -kernel kernel-qemu -cpu arm1176 -m 256 -M versatilepb -no-reboot -serial stdio\
    \ -append \"root=/dev/sda2 panic=1 rootfstype=ext4 rw \" -hda\n\nNote 2: remember\
    \ to undo the preparation steps before transferring your image to the SD card.\n\
    \n"
