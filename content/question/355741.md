    I was running into a two-part problem here, for those who run across this question:

    1. Absolute symlinks in the target sysroot. This is remedied using the `symlinks` utility https://linux.die.net/man/8/symlinks within the sysroot before exporting it for use.
    2. Fast-RTPS is exporting a dependency as an absolute path in its built debian installation. I have reported this issue here https://github.com/eProsima/Fast-DDS/issues/1264 and can manually work around it by symlinking the offending library

    ```
    ln -s sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so /usr/lib/aarch64-linux-gnu.so
    ```

    This effectively resolves the problem for this case, though a resolution of the reported packaging bug will be better.

I'm cross-compiling a ROS2 workspace for arm64 on an amd64 platform. I've created a sysroot containing the workspace dependencies. Note that I am not building the ROS2 core from source, I am only building a few small toy packages, after having exported a sysroot that has their dependencies installed (e.g. ament_cmake, rclcpp, rclpy, rosidl_default_generators, rosidl_default_runtime) Using the below toolchain, I am able to build simple packages depending on rclcpp or rclpy, but a package using rosidl to generate messages looks for tinyxml2 in the host root, rather than the target sysroot. (example package is called `cc_msgs`.

    make[2]: *** No rule to make target '/usr/lib/aarch64-linux-gnu/libtinyxml2.so', needed by 'libcc_msgs__rosidl_typesupport_fastrtps_cpp.so'.  Stop.

My question is, how can I discover where this path is being generated so that I can fix it to find tinyxml2 in the correct location?

The library in question does exist in the target sysroot, and all other needed libraries are being discovered there

    $ ls /sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so
    /sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so

The toolchain file looks like the following

    #Specific
    set(TRIPLE aarch64-linux-gnu)
    set(PY_VERSION 38)
    set(CMAKE_SYSTEM_PROCESSOR aarch64)
    
    set(SYSROOT /sysroot)
    set(ROS_WS_INSTALL_PATH /ros_ws/install)
    
    
    # Generic
    function(require_env name)
    if("$ENV{${name}}" STREQUAL "")
        message(FATAL_ERROR "Required environment variable ${name} not defined")
    endif()
    endfunction()
    
    require_env(SYSROOT)
    require_env(ROS_WS_INSTALL_PATH)
    require_env(ROS_DISTRO)
    
    set(CMAKE_SYSTEM_NAME Linux)
    SET(CMAKE_SYSTEM_VERSION 1)
    
    set(CMAKE_C_COMPILER /usr/bin/${TRIPLE}-gcc)
    set(CMAKE_CXX_COMPILER /usr/bin/${TRIPLE}-g++)
    
    set(CMAKE_SYSROOT $ENV{SYSROOT})
    set(OPENSSL_ROOT_DIR $ENV{SYSROOT}/usr/lib/aarch64-linux-gnu)
    
    set(CMAKE_FIND_ROOT_PATH $ENV{ROS_WS_INSTALL_PATH})
    set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
    set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
    set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
    set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
    
    set(PYTHON_SOABI cpython-${PY_VERSION}m-${TRIPLE})
    set(THREADS_PTHREAD_ARG "0" CACHE STRING "Result from TRY_RUN" FORCE)


The build is invoked as

    source /sysroot/opt/ros/foxy/setup.bash
    colcon build \
      --cmake-args -DCMAKE_VERBOSE_MAKEFILE:BOOL=ON -DCMAKE_TOOLCHAIN_FILE=/toolchains/aarch64-gnu.cmake --no-warn-unused-cli


EDIT: Additional investigation - If I try to build rosidl_typesupport_fastrtps_cpp in this process, it fails to find /usr/lib/aarch64-linux-gnu/libdl.so - which exists in the sysroot as well. This suggests that the issue is something to do with system-level libraries using absolute rather than relative symlinks, which are then resolved to look on the host system.
