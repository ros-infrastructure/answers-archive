  body_markdown: "Hi,\n\nI just read [this page](http://wiki.ros.org/robot_localization/Tutorials/GPS%20Integration),\
    \ using two [robot_localization](http://wiki.ros.org/robot_localization) instances\
    \ makes more sense now if you use a GPS. \n\nThe problem is that [rtabmap](http://wiki.ros.org/rtabmap_ros#rtabmap)\
    \ doesn't know there is a GPS going on, it will generate its own /map -> /odom\
    \ transform, which is the localization correction after a loop closure. This transform\
    \ is relative to the starting position of the robot.\n\nWithout the GPS, a standard\
    \ setup would be:\n![image description](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/14550571761943305.jpg)\n\
    \nYou could disable map optimization from [rtabmap](http://wiki.ros.org/rtabmap_ros#rtabmap)\
    \ (`<param name=\"RGBD/OptimizeIterations\" type=\"string\" value=\"0\"/>`) to\
    \ avoid /map -> /odom publishing if the second [robot_localization](http://wiki.ros.org/robot_localization)\
    \ with GPS is publishing it too. Then use the output of the second [robot_localization](http://wiki.ros.org/robot_localization)\
    \ as input odometry for rtabmap node. The map will be created using poses including\
    \ the GPS, so in some way the map will be already optimized (no loop closure detection\
    \ required). There may be \"jumps\" in the generated map though when a GPS localization\
    \ occurs. Note that the following is just an idea (I've never tested a system\
    \ like that):\n\n![image description](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/1455058724610265.jpg)\n\
