    I think it's safe to say that, in general, you'd not use fork/exec within a ROS node. <code>roslaunch</code> serves that purpose for most cases.

    You cited actionlib for your threading example. Yes, <code>spinOnce</code> is a proper (and non-buggy) way of handling callbacks. In this context, realize that ROS provides three types of inter-node interaction:

     - publish/subscribe is non-blocking and stateless (see '*Note' below)
     - service calls are blocking and stateful
     - actionlib calls are non-blocking and stateful

    One uses an actionlib client when other 'work' needs to be done while the action is executing; that is, one thread will perform that 'work' while another keeps track of the action's progress. ROS's <code>spin</code> is a <i>terminal</i> call (i.e., non-returning until the node shuts down), with the effect that all message processing must be handled within the callbacks (and processing will <i>only</i> be done in the callbacks). Clearly that's inadequate for the other 'work'.

    As an example, let's take a GUI for...oh, anything long-running, say navigation or object recognition. The 'work' that needs to be done is keeping the user interface responsive -- blocking the UI thread is a non-starter. For navigation, you likely want to update some representation of the current state with the actionlib feedback as it's received while the user interacts with other parts of the UI. For object recognition, it's likely not the <i>feedback</i> that's important, but rather the final <i>results</i> -- while the scene is being analyzed, the user (or the system internally) can 'work on' other things.

    Some previously asked/answered <code>spinOnce</code> questions that you may want to look at:

     - <a href="http://answers.ros.org/question/65735/is-spinonce-needed/">Is spinOnce needed?</a>
     - <a href="http://answers.ros.org/question/11887/significance-of-rosspinonce/">Significance of ros::spinOnce?</a>
     - <a href="http://answers.ros.org/question/53055/ros-callbacks-threads-and-spinning/">ROS callbacks, threads and spinning</a>

    *Note: in fact, it's exactly <code>spinOnce</code> that allows pub/sub to be non-blocking, as <code>spin</code> is terminal, and thus effectively blocks.
