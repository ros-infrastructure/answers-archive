  body_markdown: "Hi, I also recently noticed that the description in the tutorial\
    \ is a bit misleading, as the base_footprint described there is not rigidly attached\
    \ to the robot as it is the case with most robot models out there. I'll have to\
    \ think about how improve the description :)\n\nNow for your specific problem:\
    \ Yes, you have to get to transform from the IMU published to tf. If your robot\
    \ actually experiences significant roll/pitch motion, that is. If it doesn't,\
    \ the 'base_stabilized' frame is not needed, as described in the tutorial.\n\n\
    I uploaded a very simple helper node for publishing roll/pitch attitude data from\
    \ imu to tf just a few minutes ago [here](http://code.google.com/p/tu-darmstadt-ros-pkg/source/browse/#svn%2Ftrunk%2Fhector_slam%2Fhector_imu_attitude_to_tf)\
    \ (not yet indexed on ros.org).\nSo what should work is the following: Copy/Use\
    \ the [example.launch](http://code.google.com/p/tu-darmstadt-ros-pkg/source/browse/trunk/hector_slam/hector_imu_attitude_to_tf/launch/example.launch)\
    \ and use your imu topic there. For the base_frame you have to use a body-fixed\
    \ frame of your robot, let's use 'base_footprint' as an example. You now only\
    \ have to get your odometry publisher to publish 'base_stabilized \u2192 odom'\
    \ instead of 'base_footprint \u2192 odom'.\n\nFor hector_mapping you can then\
    \ set the following parameters:\n\n    <param name=\"pub_map_odom_transform\"\
    \ value=\"true\"/>\n    <param name=\"map_frame\" value=\"map\" />\n    <param\
    \ name=\"base_frame\" value=\"base_stabilized\" />\n    <param name=\"odom_frame\"\
    \ value=\"odom\" />\n\nLet me know if that works for you.\n"
