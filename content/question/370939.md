    \nYou can use subscriber status callbacks for this. See #q335811 and #q11327.\n\
    \nFor the details, see the documentation for [NodeHandle::advertise<..>(..)](https://docs.ros.org/en/api/roscpp/html/classros_1_1NodeHandle.html#ae4711ef282892176ba145d02f8f45f8d):\n\
    \n> Advertise a topic, with most of the available options, including subscriber\
    \ status callbacks\n> \n> This call connects to the master to publicize that the\
    \ node will be publishing messages on the given topic.\n> This method returns\
    \ a Publisher that allows you to publish a message on this topic.\n> \n> This\
    \ version of advertise allows you to pass functions to be called when new subscribers\
    \ connect and disconnect.  With bare functions it can be used like so:\n> \n>\
    \     void connectCallback(const ros::SingleSubscriberPublisher& pub)\n>     {\n\
    >       // Do something\n>     }\n>     handle.advertise<std_msgs::Empty>(\"my_topic\"\
    , 1, (ros::SubscriberStatusCallback)connectCallback);\n> \n> With class member\
    \ functions it can be used with boost::bind:\n> \n>     void MyClass::connectCallback(const\
    \ ros::SingleSubscriberPublisher& pub)\n>     {\n>       // Do something\n>  \
    \   }\n> \n>     MyClass my_class;\n>     ros::Publisher pub = handle.advertise<std_msgs::Empty>(\n\
    >       \"my_topic\", 1, boost::bind(\n>         &MyClass::connectCallback, my_class,\
    \ boost::placeholders::_1));\n\nThe callback will be called whenever subscription\
    \ state changes.\n\n> At any one time, only a small number of the final output\
    \ topics will actually be needed so it would be great if the information about\
    \ which computation is necessary could ripple back through the network of nodes\
    \ with each node automatically unsubscribing to the inputs that aren't relevant\
    \ to the given outputs, and then resubscribing again as and when they recieve\
    \ new subscribers to the relevant topic.\n> \n> (I know lazy publishing is a thing,\
    \ and you can check how many subscribers there are before doing the computational\
    \ work needed to publish on a topic - but that doesn't help here with chains of\
    \ nodes)\n\nFrom your description it does sound like services or actions would\
    \ be a better choice for the kind of interaction you're trying to implement.\n\
    \nIf work should be done when a client *wants it*, publish-subscribe is not the\
    \ best pattern to use, as it completely decouples everything, including *when*\
    \ something is to be done (ie: the time dimension).\n\nServices and actions place\
    \ the client firmly in control over when work should be performed.\n\nUsing creation\
    \ and destruction of subscriptions to signal that seems like a poor substitute.\n\
    \n---\n\nEdit: an alternative could be to use [ros::topic::waitForMessage(..)](http://docs.ros.org/en/api/roscpp/html/namespaceros_1_1topic.html#a4e453361e14e6f4dfac250eca087445c)\

My basic problem is that there is a chain of nodes all doing heavy computational work and all publishing the results to lots of intermediate topics. At any one time, only a small number of the final output topics will actually be needed so it would be great if the information about which computation is necessary could ripple back through the network of nodes with each node automatically unsubscribing to the inputs that aren't relevant to the given outputs, and then resubscribing again as and when they recieve new subscribers to the relevant topic.

(I know lazy publishing is a thing, and you can check how many subscribers there are before doing the computational work needed to publish on a topic - but that doesn't help here with chains of nodes)

What I want could be achieved if I could have a callback triggered in the event of a new subscription/unsubscription. I could hack this with timers and polling getNumSubscribers() but callbacks would be much better.
