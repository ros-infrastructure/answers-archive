    \ so you probably should too.\"  \n\nThere are some possibilities for improvements,\

title: QoS settings for /joint_states in Humble
upvote_count: 2
---
I've seen some packages/robots using rclcpp::SensorDataQoS() to publish the /joint_states topic.  This can create issues with existing code.  A subscriber with the default settings (Reliable) cannot subscribe to a topic published as SensorDataQoS (best effort).  There is [little documentation](https://github.com/ros2/ros2_documentation/issues/569) about how to use different QoS types, or how to check them.  

Is there an official specification as to what QoS settings certain topics, like joint_states, should be using?  

Making a topic reconfigurable is fairly trivial, but still needs to be done.  [rclpy](https://github.com/ros2/rclpy/blob/6f7cfd0c73bda1afefba36b6785516f343d6b634/rclpy/rclpy/qos_event.py#L185) and [rclcpp](https://github.com/ros2/rclcpp/blob/c24e485084f421292734ebf6b63f1a105a2c7602/rclcpp/src/rclcpp/subscription_base.cpp#L259) both treat incompatible QoS settings as a warnings.  If you're not paying attention then you're in for a fun time figuring out why it's not working, especially if you're launching something big like a robot Moveit config.

Some packages, like [robot_state_publisher](https://github.com/ros/robot_state_publisher/pull/179), have updated their main/rolling branch and default to using SensorDataQoS().  robot_state_publisher even makes it reconfigurable at launch, if you really want to set it to reliable.  I'm assuming this will make it into Humble.

[ros_controllers](https://github.com/ros-controls/ros2_controllers/blob/76bf6ae70c432565c8767fba14c9adc75028292e/joint_state_broadcaster/src/joint_state_broadcaster.cpp#L156) is using SystemDefaultsQoS(), but it's a publisher so it's not a big deal, as a SensorDataQoS() subscriber can still receive this.  

Moveit2's [planning_scene_monitor](https://github.com/ros-planning/moveit2/blob/main/moveit_ros/planning/planning_scene_monitor/src/current_state_monitor_middleware_handle.cpp#L65) is still using a subscriber with the default reliable QoS.  This will not work with a best effort publisher.

[Humble](https://discourse.ros.org/t/upcoming-branch-for-humble-starting-on-april-18th/25000) is coming out soon.  Should all packages that receive joint_states be updated, or does it fall onto publishers to be reconfigurable?  Does it make sense to default to sensor_data type subscribers like [ros2 topic echo](https://github.com/ros2/ros2cli/blob/c4b993d34aed110ef3c00a576927cb89b0ce87ec/ros2topic/ros2topic/verb/echo.py#L41), as they can receive anything?
