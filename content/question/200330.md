    Technically, I don't think the callbacks are actually <i>random</i>; rather, they occur in the order in which messages are received...even though that may appear to be random. I mention that because it indicates a fundamental misunderstanding of the mechanism: <i>you</i> do not call the callbacks, the callbacks are event-driven, ordered by message reception.

    With that said, you want to impose some kind of message reception synchronization. Perhaps something in the <a href="http://wiki.ros.org/message_filters">message_filters</a> package will do? Specifically, it seems to me that <a href="http://wiki.ros.org/message_filters/ApproximateTime">ApproximateTime</a> would work for you.

    If not, off the top of my head, a simple solution would be to use the callbacks to store message values then call a common method. The common method short-circuits unless both message values are filled, otherwise processing the stored values in the order you specify.

    It's important to note that the callback mechanism already imposes per-message synchronization (unless you're multi-threading); that is, only one callback executes at any time, and does so to completion. So implementation is straightforward -- you can simply have a boolean flag for each message type, only performing full processing when both are true.

    One final (unrelated) point: you do not need two <code>NodeHandle</code> objects, as they are reference-counted copies of a global object. See <a href="http://wiki.ros.org/roscpp/Overview/NodeHandles">NodeHandle Overview</a> or, for more detail, the <a href="http://docs.ros.org/indigo/api/roscpp/html/classros_1_1NodeHandle.html">NodeHandle API</a> (specifically the <a href="http://docs.ros.org/indigo/api/roscpp/html/classros_1_1NodeHandle.html#a0eae6a7fd8c216c3f0860aec44ca81ba">default constructor</a>).
