  body_markdown: "Yes, of course. The easiest is to generate debian packages using\
    \ bloom. Then users can simply install them on their computer as normal package.\
    \ There are many informations about this in ROS wiki and `industrial_ci` supports\
    \ also some pre-release checks which are good to do before you generate packages.\n\
    \nHere is an part of the script how we do this in a project using GH-Actions to\
    \ automatically generate packages. The commands are actually bash-compatible,\
    \ so you should be able to replicate things locally.\n\n    - name: Industial\
    \ CI build\n      uses: 'ros-industrial/industrial_ci@master'\n    \n    - name:\
    \ Install deployment dependencies  # other dependencies should be already installed\
    \ by industrial_ci\n      run: |\n        sudo DEBIAN_FRONTEND=noninteractive\
    \ apt -y install python3-catkin-tools fakeroot python3-argcomplete python3-bloom\
    \ dh-make\n    \n    - name: Generate DEBs\n      env:\n        PACKAGE_SOURCE_DIR:\
    \ ${{ env.BASEDIR }}/target_ws/src/PACKAGE/\n      run: |\n        ls -al ${{\
    \ env.BASEDIR }}\n        ls -al ${{ env.BASEDIR }}/target_ws/src/PACKAGE\n  \
    \      source ${{ env.BASEDIR }}/target_ws/install/setup.bash\n    \n        cd\
    \ ${{ env.BASEDIR }}\n    \n        bloom-generate rosdebian --os-name ubuntu\
    \ --os-version ${{ env.OS_CODE_NAME }} --ros-distro ${{ env.ROS_DISTRO }} ${{\
    \ env.PACKAGE_SOURCE_DIR }}\n        mv debian ${{ env.PACKAGE_SOURCE_DIR }}\n\
    \        cd ${{ env.PACKAGE_SOURCE_DIR }}\n        echo \"Building debian package\"\
    \n        fakeroot debian/rules binary\n    \n        rm -r obj-x86_64-linux-gnu\n\
    \        rm -r debian\n    \n        cd ${{ env.PACKAGE_SOURCE_DIR }}/..\n   \
    \     echo \"All generated packages: \"\n        ls -al ros-${ROS_DISTRO}-*deb\n\
    \        deb_name_original=`ls ros-${ROS_DISTRO}-*amd64.deb`\n        deb_name=\"\
    ${deb_name_original:0:${#deb_name_original}-4}\"\n        deb_name=\"${deb_name}.deb\"\
    \n        mv $deb_name_original $deb_name\n        echo \"Current generated deb\
    \ is: $deb_name\"\n        ls -al ros-${ROS_DISTRO}-*deb\n    \n        # Install\
    \ PACKAGE dependencies and test install the package\n        sudo DEBIAN_FRONTEND=noninteractive\
    \ apt -y install ./$deb_name\n        sudo DEBIAN_FRONTEND=noninteractive apt\
    \ --fix-broken -y install\n        sudo DEBIAN_FRONTEND=noninteractive apt -y\
    \ install ./$deb_name\n    \n        sudo apt remove -y ros-${ROS_DISTRO}-package\n\
    \n"

  body_markdown: "In c++ it's naturally separated into libraries that you can choose\
    \ to install into the debian package. However by default python is installed in\
    \ the script form for greater portability. And then some platforms will generate\
    \ the pyc locally for optimization.\n\nIn python it is possible to distributed\
    \ binary artifacts. You can use `pyc` distributions [1] there are pros and cons[2].\
    \ \n\nNone of the standard ROS toolchains are setup to do that in the open source\
    \ project we generally do not work to hide or suppress our source code. Note that\
    \ these techniques will protect against things like decompiling your released\
    \ code.\n\n\n[1] https://stackoverflow.com/questions/33399250/is-it-possible-to-make-a-pyc-only-distribution\n\
    \n[2] https://www.curiousefficiency.org/posts/2011/04/benefits-and-limitations-of-pyc-only.html"
