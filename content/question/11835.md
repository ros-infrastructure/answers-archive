  body_markdown: "Your ROS packages should belong to one or more repositories. Each\
    \ repository contains one or more [packages](http://www.ros.org/wiki/Packages),\
    \ the build dependency units.\n\nWhen creating a new package, choose the name\
    \ carefully: \n\n * Package names are global to the entire ROS ecosystem.\n *\
    \ They are messy to change later.\n * Try to pick names that will make sense to\
    \ others who may wish to use your code.\n * Package names should start with a\
    \ letter, and contain only letters, numbers and '`_`' characters. Lower case is\
    \ preferred. Feel free to [browse the current list](http://www.ros.org/browse/list.php)\
    \ for inspiriation.\n\nEach package can be built separately, so pay attention\
    \ to dependencies. The package dependency graph *must* be acyclic, i.e. no package\
    \ may depend on another that directly or indirectly depends on it.\n\n * The overhead\
    \ of a ROS package is not large. Define separate packages wherever they make sense.\n\
    \ * Avoid combining nodes that pull in mutually unneeded dependencies.\n * To\
    \ eliminate unnecessary build overhead, avoid combining nodes that are often used\
    \ separately.\n * If programs with similar dependencies are generally used together,\
    \ consider combining them into a single package.\n * If some nodes have common\
    \ dependencies on shared code that you do not wish to export publicly, they can\
    \ be combined internally within a single package.\n * If the shared code should\
    \ be exported, consider making it a separate package that the others depend on.\
    \ (This is reasonable, but not required. A single package can export libraries\
    \ and headers as well as nodes.)\n * **Consider combining message definitions\
    \ in one or more separate packages.** That usually simplifies the dependencies\
    \ among packages, with nodes depending on the messages, and not so much on each\
    \ other.\n\n"
