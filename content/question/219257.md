  body_markdown: "I've made this rough workaround which does not represent the property\
    \ of inertia, but works in a similar way:\n\n    class Class {\n     public:\n\
    \      ...\n     private:\n      interactive_markers::InteractiveMarkerServer\
    \ *interactive_marker_server_;\n      geometry_msgs::Pose marker_pose_;  // initialized\
    \ in the constructor\n      ...\n    }\n    \n    void Class::interactiveMarkerCallback(const\
    \ visualization_msgs::InteractiveMarkerFeedbackConstPtr &feedback) {\n      //\
    \ avoids too fast changes in the interactive marker pose (especially for its orientation)\n\
    \      interactiveMarkerGuidance(feedback->pose, marker_pose_);  // marker_pose_\
    \ is updated every callback\n      interactive_marker_server_->setPose(feedback->marker_name,\
    \ marker_pose_, feedback->header);\n      interactive_marker_server_->applyChanges();\n\
    \    }\n    \n    void Class::interactiveMarkerGuidance(const geometry_msgs::Pose\
    \ &target, geometry_msgs::Pose &current) {\n      tf::Pose current_pose, target_pose;\n\
    \      tf::poseMsgToTF(current, current_pose);\n      tf::poseMsgToTF(target,\
    \ target_pose);\n    \n      // distance and theta represent the arrow from current\
    \ to target pose (the one given by the mouse position)\n      double distance\
    \ = tf::tfDistance(current_pose.getOrigin(), target_pose.getOrigin());\n     \
    \ double distance_sat = saturation(distance, marker_dist_min_, marker_dist_max_);\n\
    \      double theta = std::atan2(target.position.y - current.position.y, target.position.x\
    \ - current.position.x);\n    \n      // angle represents the rotation of the\
    \ MOVE_ROTATE interactive marker\n      double current_roll, current_pitch, current_yaw,\
    \ target_roll, target_pitch, target_yaw;\n      tf::Matrix3x3(current_pose.getRotation()).getRPY(current_roll,\
    \ current_pitch, current_yaw);\n      tf::Matrix3x3(target_pose.getRotation()).getRPY(target_roll,\
    \ target_pitch, target_yaw);\n      double angle = angles::shortest_angular_distance(current_yaw,\
    \ target_yaw);\n      double angle_sat = saturation(angle, marker_steer_min_,\
    \ marker_steer_max_);\n\n      tf::Transform transform;  // the transform with\
    \ no saturated values would produce the default marker behaviour\n      transform.setOrigin(tf::Vector3(distance_sat*std::cos(theta\
    \ - current_yaw), distance_sat*std::sin(theta - current_yaw), 0));\n      transform.setRotation(tf::createQuaternionFromRPY(0,\
    \ 0, angle_sat));\n      current_pose *= transform;\n    \n      tf::poseTFToMsg(current_pose,\
    \ current);\n    }\n\n    double Class::saturation(const double &value, const\
    \ double &min, const double &max) {\n      return std::min(std::max(value, min),\
    \ max);\n    }\n\nI have chosen not to add the interactive marker initialization\
    \ to keep this answer as neat as possible. Anyway it is very similar to the one\
    \ in the [Interactive Markers Tutorial](http://wiki.ros.org/rviz/Tutorials/Interactive%20Markers%3A%20Basic%20Controls).\n\
    \nAny further comments or suggestions are welcome."

Is there an easy way of implement a sort of inertia for `visualization_msgs::InteractiveMarker`?

I'm dealing with a MOVE_ROTATE InteractiveMarker in rviz and it is simple to move it too fast causing unexpected behaviour in my application. I think I could handle it with a saturation in the marker callback and a subsequent update of the pose of the marker with the satured value, but is there a neater way of accomplishing such a behaviour?

Thank you all.
