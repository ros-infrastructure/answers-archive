    \ have a 16bit image of a thermal camera. Of course there is a function to convert\
    \ it to mono8.\nBUT. If you convert it you lose a lot of space, lets say all the\
    \ values of your picture lay between\n100-500. \nNow you convert the 32 to 8 bits\
    \ space... -> you will get a totally dark grey (almost black) image.\nYou will\
    \ lose the steps in between!\n\nSo for viewing it, it will be complete rubbish,\
    \ well if the values are in big jumps like 1000 -> 10000 \n(not normal not for\
    \ a real world image)\n\nI guess you should specifiy some function to check where\
    \ your values are, and color/grey them in that range.\nSo you will still be able\
    \ to see something.\n\nViewing in that case is more difficult then just processing\
    \ ;-)\n\nRegards,\n\nChristian"

Hi!

**Working environment:**
Kubuntu 14.04 LTS
ROS Indigo (up-to-date, full desktop install)
OpenCV 2.4.8 (default from the repos)

I have a PMD nano here and managed to get it up and running using the great library [rgbd-grabber](https://github.com/youtalk/rgbd-grabber) by Yutaka Kondo. It displays 3 things - amplitude (as cv::Mat), depth (as cv::Mat) and point cloud (as PCL cloud). Now I'm trying to integrate only the PMD part of his library in my ROS infrastructure. For this purpose I have created a wrapper node around the PMDNano class, which basically has to take the output of that class (the three data structures I have mentioned above) and publish those on my ROS network. I haven't started on the point cloud part yet since I have noticed that cv_bridge has actually very limited support for the various encodings OpenCV offers. As I reference I am using the [cv_bridge.cpp](http://docs.ros.org/indigo/api/cv_bridge/html/c++/cv__bridge_8cpp_source.html) file since the ROS documentation doesn't say a lot about the encodings. I am also using this [tutorial](http://wiki.ros.org/image_transport/Tutorials/PublishingImages).

In the tutorial the **cv::Mat** image is converted to a ROS image and encoded with the string **"bgr8"**. I however have a CV_32F at my disposal. Now as far as I know what I have here is a 32bit float at hand while the encodings provided by **cv_bridge** go as far as 16bit (example: **MONO16**).

My question is basically if it will be a problem to go to **"mono8"** in this case especially considering that the published imagery is meant just for viewing and no further processing will be done with it? If it is a problem, then how do I covert CV_32F using cv_bridge's available encodings?

Thanks!
