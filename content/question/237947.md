  body_markdown: "asimat_y's answer is correct, but I'll restate the problem and solution\
    \ in greater detail to better document the problem. \n\nProblem\n=======\nThe\
    \ pose and origin of `/map` frame (as created by `navsat_transform`) is not where\
    \ you want or expect it to be. E.g:\n\n![map_and_odom](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/14669880922739843.png)\n\
    \nThis is the robot just after boot. The frame in the top-left is `/map` which\
    \ should be right under the robot because the robot is currently sitting on the\
    \ lattitude/longitude the `/map` origin should be fixed to. \n\nCause\n=======\n\
    The pose and origin of `/map` can be set using the 'datum' ros parameter in a\
    \ launch file for `navsat_transform`. However, for reasons I don't quite understand,\
    \ if you run this launch file on your robot when the robot boots (and sometimes\
    \ when you run the launch file after boot-up as well) the origin and orientation\
    \ may not be correct. \n\nThere may be other reason for changing the pose e.g.\
    \ you want to reset it in the field.\n\nSolution\n=======\nThe set_datum service\
    \ can be used to manually reset the orientation and origin of `/map`. To do this\
    \ open a terminal (making sure your ROS environment variables are configured!)\
    \ and type:\n\n    rosservice call /datum <tab>\n\nYou should then see something\
    \ like this:\n\n    user@robot_ip_address:~$ rosservice call /datum \"geo_pose:\n\
    \    position:\n        latitude: 0.0           \n        longitude: 0.0     \
    \     \n        altitude: 0.0\n    orientation:\n        x: 0.0\n        y: 0.0\n\
    \        z: 0.0\n        w: 0.0\" \n\nFill out all the relevant parameters and\
    \ then press `enter` to set the new origin and orientation. Remember that for\
    \ the orientation you must have w = 1.0 at a minimum! (x,y,z,w = 0 will result\
    \ in a NAN error). Verify that this worked by checking your frames again, e.g.\n\
    \n![map](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/1466989052254818.png)\n\
    \nNow `/map` is correctly set to the latitude/longitude that the robot is currently\
    \ sitting on. \n\nYou can also call the set_datum service from a file and change\
    \ it that way. This is preferable if you want to reset the datum regularly. To\
    \ do this in a python script, use the following code:\n\n    from geographic_msgs.msg\
    \ import GeoPose\n    from robot_localization.srv import *\n\n    rospy.wait_for_service('datum')\n\
    \    try:\n        geo_pose = rospy.ServiceProxy('datum', SetDatum)\n        response\
    \ = geo_pose(newMapPose)\n    except rospy.ServiceException, e:\n        rospy.loginfo\
    \ (\"Service call failed: %s\"%e) \n\nWhere `newMapPose` is a [GeoPose](http://docs.ros.org/jade/api/geographic_msgs/html/msg/GeoPose.html)\
    \ message containing the coordinates you want to reset your frame origin to."

I'm trying to use `navsat_transform` and I'm having difficulty with the global frame origin not matching the latitude and longitude I'm setting it to in the launch file. For more on *that* particular problem, see [here](http://answers.ros.org/question/237305/localisation-inaccurate-and-mapodom-frames-origins-move/).

So I want to use the navsat_transform `set_datum` service to manually set the origin, as described in the [GPS Integration tutorial](http://wiki.ros.org/robot_localization/Tutorials/GPS%20Integration). However the link to the robot_localization/SetDatum service message is broken (try it [here](http://docs.ros.org/api/robot_localization/html/msg/SetDatum.html)) and I can't find anything about it in the source API. 

I've tried: 

    rosservice call /set_datum <tab>

Like a conventional set_pose service, but that doesn't work. Does anyone know how to use the set_datum service correctly? Or otherwise manually change it after launch?
