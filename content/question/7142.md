    This is actually very timely, since I just submitted a [pull request](https://bitbucket.org/osrf/gazebo/pull-request/1218/change-behavior-of-odejoint-setvelocity/diff) to change the way that `Joint::SetVelocity` works. In ODE, a torque-limited speed constraint is used with `SetVelocity` and `SetMaxForce`. In the other physics engines, however, `SetVelocity` is akin to resetting the initial conditions. It also behaves differently for long chains in the maximal coordinate solvers (ODE, Bullet) and minimal coordinate solvers (Simbody, DART). For ODE and Bullet (as of [pull request 1218](https://bitbucket.org/osrf/gazebo/pull-request/1218/change-behavior-of-odejoint-setvelocity/diff)), `SetVelocity` will set the velocity of a single child link relative to the parent link, while the minimal coordinate solvers will set the velocity of all subsequent child links down the rest of the chain. I'm going to create an issue to document this difference until I have a chance to fix it.

  body_markdown: "I just experienced the same issue and managed to solve it without\
    \ awkward workarounds (like the ones suggested by other answers).\n\nPosting the\
    \ solution here in case it helps anyone:\n\n**1. Remove the `pid_gains` configuration\
    \ specified for `/gazebo_ros_control`:**\n\nYou should not have the following\
    \ loaded as part of any launch files:\n\n    /gazebo_ros_control:\n      pid_gains:\n\
    \        base:\n          p: 10\n          i: 1\n          d: 1\n\nThe reason\
    \ is because there's a condition in gazebo controller integration (called gazebo_ros_control)\
    \ that switches between \"Force\" mode and \"Velocity\" mode depending on whether\
    \ the pid configuration is specified. If you don't have this config, the plugin\
    \ will complain:\n\n    No p gain specified for pid.  Namespace: /gazebo_ros_control/pid_gains/base\n\
    \nThis sounds like a problem that must be fixed, so of course you go and set the\
    \ pid_gains. That will switch the trajectory controller into `VELOCITY_PID` mode\
    \ that does not work in Gazebo (due to issues described by DongDong above).\n\n\
    (https://github.com/ros-controls/gazebo_ros_control/blob/jade-devel/src/default_robot_hw_sim.cpp#L201-L223)\n\
    \n    // Initialize the PID controller. If no PID gain values are found, use joint->SetAngle()\
    \ or\n    // joint->SetVelocity() to control the joint.\n    const ros::NodeHandle\
    \ nh(model_nh, robot_namespace + \"/gazebo_ros_control/pid_gains/\" +\n      \
    \                        joint_names_[j]);\n    if (pid_controllers_[j].init(nh,\
    \ true))\n    {\n      switch (joint_control_methods_[j])\n      {\n        case\
    \ POSITION:\n          joint_control_methods_[j] = POSITION_PID;\n          break;\n\
    \        case VELOCITY:\n          joint_control_methods_[j] = VELOCITY_PID;\n\
    \          break;\n      }\n    }\n    else\n    {\n      // joint->SetMaxForce()\
    \ must be called if joint->SetAngle() or joint->SetVelocity() are\n      // going\
    \ to be called. joint->SetMaxForce() must *not* be called if joint->SetForce()\
    \ is\n      // going to be called.\n      joint->SetMaxForce(0, joint_effort_limits_[j]);\n\
    \    }\n\nIn the code above, you can see that not specifying pid configuration\
    \ makes it drop into the `else` block and call `SetMaxForce` so that it can use\
    \ `SetVelocity` later to directly set the joint velocity, instead of going through\
    \ its broken velocity PID controller. Here's where it does that, just below in\
    \ the same file:\n\n    case VELOCITY:\n      sim_joints_[j]->SetVelocity(0, e_stop_active_\
    \ ? 0 : joint_velocity_command_[j]);\n      break;\n    \n    case VELOCITY_PID:\n\
    \      double error;\n      if (e_stop_active_)\n        error = -joint_velocity_[j];\n\
    \      else\n        error = joint_velocity_command_[j] - joint_velocity_[j];\n\
    \      const double effort_limit = joint_effort_limits_[j];\n      const double\
    \ effort = clamp(pid_controllers_[j].computeCommand(error, period),\n        \
    \                          -effort_limit, effort_limit);\n      sim_joints_[j]->SetForce(0,\
    \ effort);\n      break;\n\nIf you don't have `pid_gains` it would cause the `VELOCITY`\
    \ to be used, which sets velocity and works fine. If you have pid_gains it uses\
    \ `VELOCITY_PID` and freaks out because the physics simulation doesn't have enough\
    \ resolution for it to work.\n\nWhich brings us to...\n\n**2. Ensure the inertias\
    \ specified for the links are absolutely correct!**\n\nIncorrect inertias can\
    \ cause the simulation to completely blow up, or move in tiny amounts for no particular\
    \ reason, which is very irritating to watch. I recommend the following:\n\n- Set\
    \ the center of gravity for each link to something other than its origin. The\
    \ origin of the coordinate frame is almost always not the same as the actual center\
    \ of gravity for an object. It's very convenient to set the coordinate frame origin\
    \ to the point the link rotates around, but the center of gravity tends to be\
    \ near the center of the link.\n\nIt can be set by modifying the `xyz` attribute\
    \ of the `origin` tag inside `inertial` tag.\n\n    <inertial>\n        <origin\n\
    \            rpy=\"0 0 0\"\n            xyz=\"0.20328210 -0.00230698 -0.00000001\"\
    \n        />\n        <mass value=\"0.63998399\" />\n        <inertia\n      \
    \      ixx=\"0.00026130\"\n            ixy=\"0.00059318\"\n            ixz=\"\
    -0.000000001\"\n            iyy=\"0.01189494\"\n            iyz=\"0.000000001\"\
    \n            izz=\"0.01212353\"\n        />\n    </inertial>\n\n- Set the `inertia`\
    \ attributes (inside `inertial` tag) to valid values, which should be specified\
    \ with reference to the center of gravity. You can set a very rough approximation\
    \ like what the original poster recommended above:\n\nhttps://answers.gazebosim.org/question/7142/strange-behaviour-of-robot-model-when-using-jointsetvelocity-velocityjointinterface/?answer=7163#post-id-7163\n\

    \ of gravity by looking at Inertial visualization in Gazebo.\n\nIn Gazebo, click\
    \ View -> Inertias.\n\nThere should be a translucent magenta box around each joint,\
    \ roughly covering the majority of the joint, and being oriented accordingly.\n\

    \ actually follow that shape - so I am not just talking about the joint transform\
    \ being applied to the inertia to orient it, I am talking about the orientation\
    \ encoded inside the two `ix_` and `iy_` vectors. The inertia itself is oriented\
    \ to follow the geometry of the link like a \"shrink-wrapped\" convex hull averaged\
    \ as a box.\n\nIf you want the exact center of gravity and inertia, I recommend\

    \ Gravity, and three types of inertial values for you: Principal, Global, and\
    \ Center of Gravity. I then take the inertial values from Center of Gravity. There\
    \ might be a trial you can get just to calculate your stuff and move on.\n\n\n\

Dear all,

the problem stated in the title of this question is a real blocker for us at the moment.  

**What we try to do:**  
Our setup is: Trusty, Indigo, gazebo2\_2.2.3-1~trusty\_amd64

We try to simulate two 7-DoF arms:  
- Schunk lwa4d  
- Schunk lwa4p  
Models can be found [here](https://github.com/ipa-fxm/schunk_modular_robotics/tree/indigo_dev/schunk_description/urdf/lwa4d) for lwa4d and [here](https://github.com/ipa-fxm/schunk_modular_robotics/tree/indigo_dev/schunk_description/urdf/lwa4p_extended) for lwa4p_extended

We try to control those robots using ```velocity_controllers/JointVelocityController```s which uses the ```VelocityJointInterface``` hardware interface (specified in transmission). Velocity commands will finally be sent from a higher level node. For testing we simply use a terminal publisher or ```rqt```. 

To reproduce the behaviour described below, there exist convenience "bringup"-packages containing all launch- and config files [here](https://github.com/ipa-fxm/schunk_robots/tree/test_gazebo_setvelocity).  

Simply run either  
```roslaunch schunk_lwa4d lwa4d_sim_urdf.launch``` or  
```roslaunch schunk_lwa4p_extended lwa4p_extended_sim_urdf.launch``` respectively.


**The problem we are having**  
It seems that (for some) joints, the velocity commands cannot be executed by the simulated robot. I.e. the current joint velocity (as published in ```/joint_states/velocity``` differs from the velocity command being send from the (forward command) controller ```velocity_controllers/JointVelocityController``` (on topic ```/arm_X_joint_velocity_controller/command```).

The following videos visualize the current behaviour.  
In [video1](https://www.dropbox.com/s/0fzb8390600xvpi/lwa4p_extended_drop_init.mp4?dl=0) it can be seen that ```arm_2_joint``` of the Schunk lwa4p_extended already starts to drop/drift right from the beginning of the simulation, i.e. whon no velocity command has yet been send and thus goal velocity is 0.0 for all joints.  
In [video2](https://www.dropbox.com/s/gxcpvog4fkl6vdk/lwa4p_extended_command_velocities.mp4?dl=0) it can be seen that also commanding velocities != 0.0 are not executed correctly.  
However in [video3](https://www.dropbox.com/s/cwtyu022qlnqjzv/lwa4d_command_velocities.mp4?dl=0) it can be seen that velocity commands actually can be executed without dropping/drifting. (Beside the strange behaviour of arm\_6\_joint! As this is also of the same motor type as used in the lwa4p\_extended, I assume that the behaviour of that arm\_6\_joint has similar reasons.)  

**What we already tried to fix it**  
Of course, I found the following related threads on this list:  

- In [this thread](http://answers.gazebosim.org/question/2743/setting-joint-velocity-through-plugin/) and [this thread](http://answers.gazebosim.org/question/5226/setting-joint-velocity-from-a-plugin/) it is suggested to check ```SetMaxForce```. However, as I am using the ```gazebo_ros_control``` plugin with ```DefaultRobotHWSim``` hardware interface, the value passed to ```Joint::SetMaxForce``` is received from the effort limit in the URDF. We use values from the technical data sheets of our motors for our model but of course also tested (arbitrarily) higher values - without success.

- In [this thread](http://answers.gazebosim.org/question/4294/joints-drift-when-they-are-not-being-driven-or/) the problem was caused by a wrong inertia tag in the URDF. However, in our models, we use inertias derived from CAD data. We also tried to use "simplified" approximations for the inertias using [these macros](https://github.com/ipa-fxm/cob_common/blob/indigo_dev/cob_description/urdf/common.xacro) - again: no success.

We also played around with the meshes used for our models in order to guarantee they don't collide thus causing unexpected forces to the joints - again: no success.

What other possible solutions could we test in order to pin down the source of error? Any ideas?
