  body_markdown: "I agree with Mac's answer. \n\nI had this discussion with Blaise\
    \ Gassend a year or so ago. He said the `level` parameter is just a bit mask.\
    \ It can be used to classify sets of parameters in any way that is convenient\
    \ to the package defining the server. The bits for all parameter classes that\
    \ have changed will be `ORed` together for the service callback.\n\nOne useful\
    \ classification scheme is suggested by the `driver_base` states: \n\n 1. Parameters\
    \ that can only be changed while the device is closed.\n 2. Parameters that can\
    \ be changed while the device is not streaming.\n 3. Parameters that can be changed\
    \ while the device is open and streaming.\n\nBut, servers are free to classify\
    \ their parameters any way they like."

title: What are the semantics of 'reconfiguration level' for dynamic reconfigure?
upvote_count: 10
---
In the [dynamic_reconfigure tutorial](http://www.ros.org/wiki/dynamic_reconfigure/Tutorials/SettingUpDynamicReconfigureForANode#preview), it is claimed that dependence on `driver_base` is specific to the tutorial, yet an enum type from `driver_base` is used to set the 'reconfiguration level'. 

Is this just a field to be interpreted however we like, and just used with the `driver_base/SensorLevels` message in this case? Or is the `driver_base/SensorLevels` message *the* standard for the 'reconfiguration level' field semantics?
