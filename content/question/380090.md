  body_markdown: "Note: you tagged this `melodic`, meaning ROS 1. This answer would\
    \ be significantly different in a ROS 2 context, where [DDS QoS allows to configure\
    \ such properties as history and durability](https://docs.ros.org/en/foxy/Concepts/About-Quality-of-Service-Settings.html).\n\
    \nAs for ROS 1:\n\n> I'd like to know if, in general, it is possible to access\
    \ the n last messages from a rostopic using a callback function for instance,\
    \ in one shot ?\n\nno, pub-sub is implemented in such a way that all participants\
    \ must be on-line at the same time to receive messages.\n\nSee #q203129 for a\
    \ related question.\n\nThere is one \"exception\" and that would be [latched topics](http://wiki.ros.org/roscpp/Overview/Publishers%20and%20Subscribers#Publisher_Options):\n\
    \n> `latch` [optional]\n> \n>    Enables \"latching\" on a connection. When a\
    \ connection is latched, the last message published is saved and automatically\
    \ sent to any future subscribers that connect. This is useful for slow-changing\
    \ to static data like a map. Note that if there are multiple publishers on the\
    \ same topic, instantiated in the same node, then only the last published message\
    \ from that node will be sent, as opposed to the last published message from each\
    \ publisher on that single topic. \n\nBut that will get subscribers only the last\
    \ message published on a topic by a publisher, nothing more.\n\n> Or is it mandatory\
    \ to use a buffer system to aggregate the messages as they are published ?\n\n\
    Yes, that's typically how this is implemented.\n\nBut you don't need to write\
    \ that yourself. Use a [message_filters](https://wiki.ros.org/message_filters)\
    \ [Cache](https://wiki.ros.org/message_filters#Cache) or even better, if possible,\
    \ a [TimeSynchronizer policy](https://wiki.ros.org/message_filters#Policy-Based_Synchronizer_.5BROS_1.1.2B-.5D).\n\
    \nA community contributed alternative/improvement could be [fkie/message_filters](https://fkie.github.io/message_filters),\
    \ which adds some more flexibility and generalises the pipeline concept a bit\
    \ more.\n"
