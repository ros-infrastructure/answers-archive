    \ humble it will work like your description.\nSo my best guess is the demo you\
    \ are using contains this [commit](https://github.com/ros2/demos/commit/d9c8dacaeddbb7fd8316b1e2bd9b04160f8c6a2c),\
    \ which should only be available since humble.\n\nThe [foxy/galactic document](https://docs.ros.org/en/humble/Tutorials/Demos/Intra-Process-Communication.html#pipeline-with-two-image-viewers)\
    \ is somehow wrong:\n\n> This means the system deliveres the same shared_ptr to\
    \ both callbacks. When the first intraprocess subscription is handled, the internally\
    \ stored unique_ptr is promoted to a shared_ptr. Each of the callbacks will receive\
    \ shared ownership of the same message.\n\n[The foxy/galactic demo's ImageViewNode\
    \ callback](https://github.com/ros2/demos/blob/26e048b88ac16b52523323bb3f193d0b83dabf76/intra_process_demo/include/image_pipeline/image_view_node.hpp#L40)\
    \ used type `const sensor_msgs::msg::Image::SharedPtr` as argument, and it's **NOT**\
    \ shared ownership. Then the intra-process logic have to copy the message to make\
    \ sure each ImageViewNode will have exclusive ownership of the message dispatched\
    \ to them, which behaves the same as callbacks using type `const std::unique_ptr<sensor_msgs::msg::Image>`.\n\
    \n[The humble demo's ImageViewNode callback](https://github.com/ros2/demos/blob/f258b8182c7ad680c8cceba38eac72e01fdb0a3c/intra_process_demo/include/image_pipeline/image_view_node.hpp#L44)\
    \ changed the argument type to `sensor_msgs::msg::Image::ConstSharedPtr`, and\
    \ now it really means shared ownership. Then the demo behaves like your description,\
    \ so the humble's document should be updated to reflect this change.\n\nThe intraprocess\
    \ zero copy for multiple subscriber should always work since foxy, as long as\
    \ you are using the correct signature for callbacks.\n\nThe callback argument\
    \ type and ownership relationship can be verified using this snippet:\n\n    #include\
    \ <iostream>\n    #include <memory>\n    \n    #include <rclcpp/rclcpp.hpp>\n\
    \    #include <sensor_msgs/msg/image.hpp>\n    \n    template<typename TCallback>\n\
    \    void PrintAnyCallbackSharedOrNot(TCallback&& cb) {\n      rclcpp::AnySubscriptionCallback<sensor_msgs::msg::Image,\
    \ std::allocator<void>> acb{std::allocator<void>()};\n      acb.set(std::move(cb));\n\
    \      std::cout << acb.use_take_shared_method() << std::endl;\n    }\n    \n\
    \    int main(int , char *[]) {\n      // false\n      PrintAnyCallbackSharedOrNot([](std::shared_ptr<sensor_msgs::msg::Image>){});\n\
    \      // false, same as const sensor_msgs::msg::Image::SharedPtr\n      PrintAnyCallbackSharedOrNot([](const\
    \ std::shared_ptr<sensor_msgs::msg::Image>){});\n    \n      // true, same as\
    \ sensor_msgs::msg::Image::ConstSharedPtr\n      PrintAnyCallbackSharedOrNot([](std::shared_ptr<const\
    \ sensor_msgs::msg::Image>){});\n      // true\n      PrintAnyCallbackSharedOrNot([](const\
    \ std::shared_ptr<const sensor_msgs::msg::Image>){});\n      return 0;\n    }"

When following instructions from [Pipeline with two image viewers](https://docs.ros.org/en/galactic/Tutorials/Intra-Process-Communication.html#pipeline-with-two-image-viewers), running

```
ros2 run intra_process_demo image_pipeline_with_two_image_view
```

the expected result is that the last pointer in image_view_node_2 has a different memory address. 

**However, all the memory addresses are the same.** Does this mean zero-copy intraprocess communication works for multiple subscribers? Or is it my misunderstanding somewhere?
