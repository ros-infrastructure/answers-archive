  body_markdown: "No, I would not layout things as you have. Particularly `src` should\
    \ be reserved for source code only (ie: Python, C++, etc).\n\nNo configuration\
    \ files, no URDF nor Xacro, no Gazebo worlds, etc.\n\n> My ROS package is beginning\
    \ to get complicated with multiple folders for various aspects of functionality.\n\
    \nAs a high-level comment: try to separate things a bit. You seem to treat `my_package`\
    \ as a *mini workspace* almost. It's not.\n\nWhy not create a `my_package_gui`,\
    \ `my_package_gazebo` and `my_package_description` package? Packages are almost\
    \ free, so separate things as much as possible. Decrease coupling, separate concerns\
    \ and delegate responsibilities.\n\n---\n\nThere are various Q&As on ROS Answers\
    \ about recommended package layout.\n\nThe ROS wiki also has a few pages which\
    \ go into this, most notable [wiki/Packages](http://wiki.ros.org/Packages). It\
    \ doesn't prescribe a particular layout, but does give some examples of *common\
    \ folders* and where they are expected to be relative to a package's root.\n\n\
    An often referenced 3rd party resource on the topic of best practices is [leggedrobotics/ros_best_practices](https://github.com/leggedrobotics/ros_best_practices/wiki).\
    \ The section [File/Folder Structure for Packages](https://github.com/leggedrobotics/ros_best_practices/wiki#filefolder-structure-for-packages)\
    \ shows an often used example.\n\nOne thing to keep in mind: this structure is\
    \ mostly *for humans*, as `roslaunch` and `rosrun` fi don't care where you've\
    \ placed your binaries / executable scripts. They'll crawl the complete package\
    \ and its sub directories. There are certainly things which must be in a certain\
    \ location (such as the manifest and build script), but the rest is not important.\n\
    \nAnd an observation:\n\n>     catkin_ws/src/my_package\n    \u2502\n    ...\n\
    \    \u251C\u2500\u2500 venv\n    ...\n\nPersonally I would not place a Python\
    \ `venv` inside the `src` space of a Catkin workspace, but you may have good reason\
    \ to do so. You may want to look at tools such as [catkin_virtualenv](http://wiki.ros.org/catkin_virtualenv)\
    \ to manage this instead.\n\n---\n\nEdit: and I just noticed this:\n\n>     catkin_ws/src/my_package\n\
    \    \u2502\n    \u251C\u2500\u2500 cmake-build-debug\n    ..\n\nWhat is `cmake-build-debug`?\
    \ Are you doing in-source builds with `cmake` directly?\n\nI would expect build\
    \ artefacts to only exist in the `build` space of your Catkin workspace."
