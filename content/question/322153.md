  body_markdown: "Isn't the problem here that you're trying to use `image_transport::Subscriber`\
    \ to subscribe to a topic which isn't actually carrying `Image`s, but `darknet_ros_msgs::ImageWithBoundingBoxes`?\n\
    \nThat's also what the error message seems to tell you. Paraphrasing, it would\
    \ read:\n\n>     error: invalid initialization of reference of type \u2018darknet_ros_msgs::ImageWithBoundingBoxes&\u2019\
    \ from expression of type \u2018boost::shared_ptr<const sensor_msgs::Image>\n\n\
    You'll probably have to switch to a regular `ros::Subscriber` instead of using\
    \ `image_transport`'s.\n\n---\n\nEdit:\n\n> Oh, right yes... But how could I rewrite\
    \ it? So that I still can use the image_transport functionality?\n\nI'm not sure.\
    \ Possibly *not* using a custom message, but using something like [message_filters](http://wiki.ros.org/message_filters)\
    \ to combine related messages based on their timestamps (so only publish a list\
    \ of boundingboxes (one from [vision_msgs](http://wiki.ros.org/vision_msgs) preferably)\
    \ with the same timestamp as the `sensor_msgs/Image` that the detection was run\
    \ on, then later recombine the two using `message_filters`).\n\nI'm not an `image_transport`\
    \ expert though, so there could be a different option.\n\nThere is a tutorial\
    \ on writing your own transport plugin ([this one](http://wiki.ros.org/image_transport/Tutorials/WritingNewTransport)),\
    \ but I don't believe that is something that would fit your use-case.\n\n---\n\
    \nEdit 2:\n\n > Edit: Thank you! Now it works. But what I am still not sure about:\
    \ Is it now slower? Because i don't use the image transport functionality?\n\n\
    Using `image_transport` doesn't make anything magically faster. The \"only\" thing\
    \ `image_transport` does is making it easier to use different compression algorithms\
    \ (called \"transports\" in `image_transport` lingo) without having to deal with\
    \ their details in image producers and consumers. Simply configure a specific\
    \ transport to be used, and without recompiling or changing anything in your publishers\
    \ or subscribers it will be used. Transparently.\n\nIn the case of compression,\
    \ this actually has the potential to make things *slower* (as compression adds\
    \ overhead), but that obviously depends on a number of other factors (size of\
    \ images vs bandwidth, latency, etc).\n\nSo with switching to a regular `Subscriber`,\
    \ you lose all of that. But you had already lost that, as you were using a regular\
    \ `Publisher` as well."
