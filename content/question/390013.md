    I don't have an answer to your question, but I did want to mention that the modern ROS convention for Transform Frame names is to **not** use a leading slash. In fact, internally ros will strip off the *leading* slash if you put it there. An individual TF name has no hierarchical nature; it is just a string.

  I compute it myself?

I've recently been working with the ROS navigation stack using an [RPLIDAR Mapper M2M1 from Slamtec](https://www.slamtec.com/en/Lidar/Mapper). Interesting thing about this LIDAR model is that the mapping and localization is performed in-device. Running their ROS package it publishes the following transforms:

A fixed transform `/map -> /odom` filled with zeros. `/map and /odom` are always aligned.

A dynamic transform `/odom -> /base_link` that actually contains the robot's localization in the map. This is accompanied by an odometry topic (with all covariances zeroed out). Sending 2D pose estimates (e.g. from RVIZ) modifies this transform.

This setup can work with move_base and the navigation stack okayish. However, the thing is my robot also has its own internal odometry that can be published to the `/odom` topic along with a transform `/odom -> /base_link`. So now I'm looking into how to integrate these two odometry sources.

---

At first I thought I should be performing sensor fusion using the robot_localization package. But after spending some time studying, I realized that the LIDAR device should be publishing a transform to correct error in the `/map -> /odom`, while the robot's internal odometry should always be continuous and is responsible for `/odom -> /base_link`. The actual localization of the robot could then be get requesting a transform `/map -> /base_link`. Is my thinking/understanding here correct?

Assuming this is the case, and my LIDAR package doesn't publish a correction transform `/map -> /odom`, I'm thinking I could do the following:

1. Change LIDAR transforms to some dummy ones, e.g. `/map -> /lidar_odom` (the fixed one) and `/lidar_odom -> /lidar_base_link` (the LIDAR's estimate of localization).
2. Compute the difference between LIDAR's localization `/map -> (/lidar_odom ->) /lidar_base_link` AND `/map -> (/odom ->) /base_link`.
3. Use the difference as a transform to correct `/map ->/odom`.

Does this procedure seem to make sense? I'm a bit concerned this feels like a "hack" and might not be the standard way of doing things. Appreciate any input and suggestions on this matter.
