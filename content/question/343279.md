  body_markdown: "This has been a major pain point for me when porting a big ROS1\
    \ code base that made synchronous service calls all the time deep inside libraries.\
    \ My preferred solution to this is setting up the node and client so that the\
    \ service response arrives on another thread. Then the code calling the service\
    \ *can* just do `future.get()` or `future.wait()` to wait for the response. You\
    \ need to:\n\n- Create the service client using a different callback group created\
    \ using [rclcpp::Node::create_callback_group](http://docs.ros2.org/eloquent/api/rclcpp/classrclcpp_1_1Node.html#a5465f425d2fa3b3dc1df6e901eb5a608).\
    \ You can make group type [Reentrant](http://docs.ros2.org/eloquent/api/rclcpp/namespacerclcpp_1_1callback__group.html#a0dc3fb88dd5871c2230be09da1a342d4)\
    \ and then use the same group for all your callbacks or just use a separate group\
    \ for the one service client.\n\n- Spin your node with a [MultiThreadedExecutor](http://docs.ros2.org/eloquent/api/rclcpp/classrclcpp_1_1executors_1_1MultiThreadedExecutor.html)\
    \ instance.\n\nIn general I try to do this and avoid use of `spin_until_future_complete`\
    \ whereever possible because I don't want my internal application logic coupled\
    \ with the spinning/execution of my node. Maybe we'll get some API updates in\
    \ a future release that makes this easier, especially with having to handle callback\
    \ group objects explicitly.\n\nEdit: Including a full standalone example to clearly\
    \ show how to do this. Here a node calls a service advertised by the same node\
    \ from within the callback of a different service.\n\n    #include <rclcpp/rclcpp.hpp>\n\

    \    \n          outer_srv_ = this->create_service<std_srvs::srv::Trigger>(\"\
    outer_srv\",\n              std::bind(&TwoSrvs::outer_cb, this, std::placeholders::_1,\
    \ std::placeholders::_2),\n              ::rmw_qos_profile_default,\n        \
    \      callback_group_);\n    \n          inner_srv_ = this->create_service<std_srvs::srv::Trigger>(\"\
    inner_srv\",\n              std::bind(&TwoSrvs::inner_cb, this, std::placeholders::_1,\
    \ std::placeholders::_2),\n              ::rmw_qos_profile_default,\n        \
    \      callback_group_);\n    \n          client_ = this->create_client<std_srvs::srv::Trigger>(\"\
    inner_srv\");\n      }\n    \n      void outer_cb(std_srvs::srv::Trigger::Request::SharedPtr,\
    \ std_srvs::srv::Trigger::Response::SharedPtr res)\n      {\n        using namespace\
    \ std::chrono_literals;\n    \n        RCLCPP_INFO(get_logger(), \"outer srv callback\"\
    );\n    \n        auto req = std::make_shared<std_srvs::srv::Trigger::Request>();\n\
    \        auto future = client_->async_send_request(req);\n    \n        RCLCPP_INFO(get_logger(),\
    \ \"outer srv called inner srv\");\n    \n        auto status = future.wait_for(3s);\
    \  //not spinning here!\n        if (status == std::future_status::ready)\n  \
    \      {\n          RCLCPP_INFO(get_logger(), \"inner srv response is %s\", future.get()->message.c_str());\n\
    \          res->success = true;\n          res->message = \"good\";\n        }\n\
    \        else\n        {\n          RCLCPP_ERROR(get_logger(), \"inner srv future\
    \ wait failed\");\n          res->success = false;\n          res->message = \"\
    bad\";\n        }\n      }\n    \n      void inner_cb(std_srvs::srv::Trigger::Request::SharedPtr,\
    \ std_srvs::srv::Trigger::Response::SharedPtr res)\n      {\n        RCLCPP_INFO(get_logger(),\

  body_markdown: "Hi, \n\nI recently came across this issue. In ROS 1, services are\
    \ clearly different from action as they are synchronous. Porting code from ROS\
    \ 1 to 2 usually requires service calls to keep synchronous, or induces a change\
    \ in the architecture.\n\nHere is a simple wrapper to handle this:\n\n    template\
    \ <class ServiceT>\n    class ServiceNodeSync\n    {\n        typedef typename\
    \ ServiceT::Request RequestT;\n        typedef typename ServiceT::Response ResponseT;\n\
    \    public:\n        ServiceNodeSync(std::string name): node(std::make_shared<rclcpp::Node>(name))\n\
    \        {    }\n\n        void init(std::string service)\n        {\n       \
    \ client = node->create_client<ServiceT>(service);\n        client->wait_for_service();\n\
    \        }\n\n        ResponseT sendRequest(const RequestT &req)\n        {\n\
    \        return sendRequest(std::make_shared<RequestT>(req));\n        }\n\n \
    \       ResponseT sendRequest(const std::shared_ptr<RequestT> &req_ptr)\n    \
    \    {\n        auto result = client->async_send_request(req_ptr);\n        rclcpp::spin_until_future_complete(node,\
    \ result);\n        return *result.get();\n        }\n\n    protected:\n     \
    \   rclcpp::Node::SharedPtr node;\n        typename rclcpp::Client<ServiceT>::SharedPtr\
    \ client;\n    };\n\nIt can be used as a member variable (say service_node_sync)\
    \ of your base node\nThen the synchronous service call boils down to:\n\n    auto\
    \ response = service_node_sync.sendRequest(request);\n\nI guess this can be adapted\
    \ for particular uses, but for now that is basically how I can teach/introduce\
    \ ROS 2 services as being more or less the same as in ROS 1."

In ROS1, it was possible to make a (synchronous) service call from a callback.

In ROS2, in a derived node class, if I do the following:

1. create a service client using "create_client" 
2. within a callback function (e.g. a timer callback) call async_send_request() on the client and then:
3. call get() on the future that is returned

It will block forever.  Instead, I must register a callback when I call async_send_request() in order to handle the response.

An async design does have its advantages, so I am wondering, is it the intent of ROS2 to force asynchronous service message handling in a node or is there a way to do a sync call that I haven't uncovered yet?
