  body_markdown: "In short, yes.  There are multiple ways to approach this depending\
    \ on how you want to handle the messages.  You can always implement your own class\
    \ that subscribes to both topics, stores the messages, and operates on them as\
    \ you see fit.  On the other end of the spectrum, you may be able to get away\
    \ with using `topic_tools` ([wiki](http://wiki.ros.org/topic_tools)) to republish\
    \ the `sensor_msgs/CompressedImage` ([doc](https://docs.ros.org/en/melodic/api/sensor_msgs/html/msg/CompressedImage.html)),\
    \ which does have a header, on a new topic and subscribing to that one with a\
    \ `message_filters::Synchronizer` ([wiki](http://wiki.ros.org/message_filters#Policy-Based_Synchronizer_.5BROS_1.1.2B-.5D))\
    \ as before.  In between, you may be able to use the `message_filter` library\
    \ to implement a custom filter without starting from scratch.\n\nPlease, provide\
    \ more context if you'd like a more specific answer.  How do you want to handle\
    \ the messages if not time-synchronizing them?  Do you need the `unique_id` for\
    \ processing in the callback?\n\n---\n###Update\nTo clarify the discussion in\
    \ the comments, @Kansai chose the second option above.  There is enough information\
    \ in the original `Image` message defined in the question for normal synchronizing\
    \ with a `message_filters::TimeSynchronizer`, but that info is not contained in\
    \ a top-level header as expected.\n\nThe message definition contains a field called\
    \ `image` of type `sensor_msgs/CompressedImage`, which in turn contains a header.\
    \  The chosen solution therefore involves relaying the `image` field on its own\
    \ (new) topic as a standalone `CompressedImage` message, which can work with the\
    \ `TimeSynchronizer`.\n\nTo achieve the relay, one can use `topic_tools/transform`\
    \ in a launch file like so:\n\n    <launch>\n        <node name=\"pub\" pkg=\"\
    rostopic\" type=\"rostopic\"\n            args=\"pub -r 1 /original_topic test_pkg/Image\n\
    \                '{unique_id: 0, image: {header: {seq: 0, stamp: {secs: 1, nsecs:\
    \ 0}, frame_id: 'test_frame'}, format: 'png', data: '[1]'}}'\" />\n    \n    \
    \    <node name=\"relay\" pkg=\"topic_tools\" type=\"transform\"\n           \
    \ args=\"/original_topic /new_topic sensor_msgs/CompressedImage 'm.image'\"/>\n\
    \    </launch>\n\nCheck output:\n\n    $ rostopic echo /new_topic \n    header:\
    \ \n      seq: 1\n      stamp: \n        secs: 1\n        nsecs:         0\n \
    \     frame_id: \"test_frame\"\n    format: \"png\"\n    data: [1]\n    ---\n\n\
    This way the `allow_headerless` option (which would use receipt time rather than\
    \ a timestamp) is unnecessary, and better synchronization is possible.  Though\
    \ the relay node introduces some extra delay, it may be negligible for a given\
    \ application.  There are of course alternatives, but I don't want to clutter\
    \ the discussion more if this solution works for OP."

I made a similar question [here](https://answers.ros.org/question/374883/what-is-the-best-way-to-synchronize-messages/) as to how to assign a callback to two different topics. 

The answer was to use `message_filter`. I tried it and it worked. 

I am trying to do the same with two other types of topics and I got the error: 

    AttributeError: 'Image' object has no attribute 'header'

I investigated and found that the synchronization uses the time stamp in the headers of the topics. 
The problem is that now I am using two topics  and one of them is a types of messages without headers. 
 
The topic message type ("Image") is

    uint64 unique_id
    sensor_msgs/CompressedImage image

As you can see it has no headers. (therefore the error "no attribute header")

My question is, is there a way that I can still combine these two topics in one callback?
