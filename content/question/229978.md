  body_markdown: " AMCL tries to match the laser scans to the map thus detecting if\
    \ there is any drift occurring in the pose estimate based on the odometry (dead\
    \ reckoning). This drift is then compensated by publishing a transform between\
    \ the map frame and the odom frame such that at the end the transform map->base_frame\
    \ corresponds to the real pose of the robot in the world. It is explained [here](http://wiki.ros.org/amcl)\
    \ with a nice diagram:\n\n![image description](http://wiki.ros.org/amcl?action=AttachFile&do=get&target=amcl_localization.png)\n\
    \n\n[here](http://www.ros.org/reps/rep-0105.html) you can find the definitions\
    \ and uses of each frame for ROS REP105 naming conventions:\n\n> **Coordinate\
    \ Frames**\n\n> **map**\n\n> The coordinate frame called map is a\n> world fixed\
    \ frame, with its Z-axis\n> pointing upwards. The pose of a mobile\n> platform,\
    \ relative to the map frame,\n> should not significantly drift over\n> time. The\
    \ map frame is not continuous,\n> meaning the pose of a mobile platform\n> in\
    \ the map frame can change in\n> discrete jumps at any time.\n> \n> In a typical\
    \ setup, a localization\n> component constantly re-computes the\n> robot pose\
    \ in the map frame based on\n> sensor observations, therefore\n> eliminating drift,\
    \ but causing\n> discrete jumps when new sensor\n> information arrives.\n> \n\
    > The map frame is useful as a long-term\n> global reference, but discrete jumps\n\
    > make it a poor reference frame for\n> local sensing and acting. \n> \n> **odom**\n\
    > \n> The coordinate frame called odom is a\n> world-fixed frame. The pose of\
    \ a\n> mobile platform in the odom frame can\n> drift over time, without any bounds.\n\
    > This drift makes the odom frame\n> useless as a long-term global\n> reference.\
    \ However, the pose of a\n> robot in the odom frame is guaranteed\n> to be continuous,\
    \ meaning that the\n> pose of a mobile platform in the odom\n> frame always evolves\
    \ in a smooth way,\n> without discrete jumps.\n> \n> In a typical setup the odom\
    \ frame is\n> computed based on an odometry source,\n> such as wheel odometry,\
    \ visual\n> odometry or an inertia measurement\n> unit.\n> \n> The odom frame\
    \ is useful as an\n> accurate, short-term local reference,\n> but drift makes\
    \ it a poor frame for\n> long-term reference. \n> \n> **base_link**\n> \n> The\
    \ coordinate frame called base_link\n> is rigidly attached to the mobile\n> robot\
    \ base. The base_link can be\n> attached to the base in any arbitrary\n> position\
    \ or orientation; for every\n> hardware platform there will be a\n> different\
    \ place on the base that\n> provides an obvious point of\n> reference. Note that\
    \ REP 103 [1]\n> specifies a preferred orientation for\n> frames. \n> \n> **Relationship\
    \ between Frames**\n> \n> We have chosen a tree representation\n> to attach all\
    \ coordinate frames in a\n> robot system to each other. Therefore\n> each coordinate\
    \ frame has one parent\n> coordinate frame, and any number of\n> child coordinate\
    \ frames. The frames\n> described in this REP are attached as\n> follows:\n> \n\
    > map --> odom --> base_link\n> \n> The map frame is the parent of odom,\n> and\
    \ odom is the parent of base_link.\n> Although intuition would say that both\n\
    > map and odom should be attached to\n> base_link, this is not allowed because\n\
    > each frame can only have one parent.\n\n"
