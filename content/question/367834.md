  body_markdown: "Have you looked at [Unity blogs: Robotics simulation in Unity](https://blogs.unity3d.com/2020/11/19/robotics-simulation-in-unity-is-as-easy-as-1-2-3/)?\
    \ Section 3, **Connecting your simulation to ROS** states:\n\n> Now that the robot\
    \ is in the Unity\n> Editor, we should test our\n> motion-planning algorithm,\
    \ running in\n> a set of ROS nodes. To support this,\n> we need to set up a communication\n\
    > interface between Unity and ROS. Unity\n> needs to pass messages to ROS that\n\
    > contain state information \u2014 namely,\n> the poses of the robot, target object,\n\
    > and target location \u2014 along with a\n> planning request to the mover service.\n\
    > In turn, **ROS needs to return a\n> trajectory message to Unity\n> corresponding\
    \ to the motion plan**\n> (i.e., the sequence of joint positions\n> required to\
    \ complete the\n> pick-and-place task).\n\nI haven't myself tried this out but\
    \ the *Unity package* `ROS-TCP-Connector` and *ROS package* `ROS-TCP-Endpoint`\
    \ look useful to establish the bridge between Unity and ROS. On the Unity side,\
    \ a C# script could make a service request, in response to which, ROS sends back\
    \ the trajectory:\n\n> [..] makes a service request to the\n> MoveIt motion planner.\
    \ The service\n> request includes the current pose of\n> the robot, the pose of\
    \ the target\n> object, and the target location. When\n> MoveIt receives the planning\
    \ request,\n> it attempts to compute a motion plan.\n> If successful, the **service\
    \ returns the\n> plan, i.e., a sequence of joint\n> positions** [..]\n\nDepending\
    \ on your use, you may not even need a service. Set up a publisher on the ROS\
    \ side and a subscriber on the Unity side, and after the trajectory is computed\
    \ ROS simply publishes it."
