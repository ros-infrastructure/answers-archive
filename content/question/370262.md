Hello,
My team is looking into using ROS2 with a Fast DDS Discovery Server to identify and connect nodes.  We are operating in a distributed environment, and in order to facilitate operations, we were interested in setting up multiple discovery servers, one on each node, so that each node can (as needed) communicate with every other node via standard DDS topic subscription.  We've spent some time looking at the documentation as well as trying to set up a few test instances, but still have some questions.  We would really appreciate it if someone could provide insight on the following:

1. The documentation states in multiple places that servers can be clients of other servers (example: https://fast-dds.docs.eprosima.com/en/latest/fastdds/discovery/discovery_server.html#discovery-server), but it is unclear exactly what that means. Ideally, what we want it to mean is that if server A has server B as a client, then all of server B's topic registrations are shared with server A. Furthermore, we'd love it if server A and server B could be clients of each other, resulting in a full sharing of topic registration information between them. (Of course, this breaks down as you scale up, but for a limited # of nodes running a limited # of services, it should be viable, in theory.). Any information someone could provide on this arrangement, either in a single direction or bidirectional, would be very helpful.
2. From https://discourse.ros.org/t/new-discovery-server/17383/8, "Note that it’s possible to specify addresses where a server might be in the future." We did internal testing with simple pub/sub applications where we specified two servers (using the env variable ROS_DISCOVERY_SERVER), one that was currently active and one that we wanted to bring up later. We found that even though the pubs and subs were connected via the first discovery server, no messages passed between them until both of the discovery servers were started. Given the above quote, we're wondering if this is a bug or perhaps a misconfiguration on our end.
