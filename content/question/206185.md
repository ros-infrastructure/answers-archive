    \ and LPLidar. You can find a full documentation about the fix [here](http://geduino.blogspot.it/2015/04/gmapping-and-rplidar.html)\
    \ (including source code modification of course): I hope can be useful for you\
    \ too!\n\n## UPDATE ##\n\nGMapping use two parameters to define laser beam range:\n\
    \n - maxRange: the maximum range of the sensor. If regions with no obstacles within\
    \ the range of the sensor should appear as free space in the map, set maxUrange\
    \ < maximum range of the real sensor <= maxRange;\n - maxUrange: the maximum usable\
    \ range of the laser. A beam is cropped to this value.\n\n(Description taken by\
    \ ros gmapping wiki)\n\nThe long lines you see on your map are created when the\
    \ laser measured range is between maxUrange and maxRange. You can try to set maxUrange\
    \ = maxRange. By the way I think the real problem is another: why your laser measures\
    \ this range if there is a wall?\n\nCan you take a picture of RViz where laser\
    \ scan data is shown too? I suggest to set decay to 120 secs so we can see more\
    \ data. I want to check if long lines are really generated by laser measures of\
    \ if they are artefacts of GMapping.\n\n## UPDATE ##\n\nCan you register and upload\
    \ a bag file of your test? Remember to move the robot in your environment recording\
    \ data in order to have an idea of the expected map. You should record tf and\
    \ your laser scan topic.\n\nFurther question: on the posted RViz screenshot I\
    \ can see an entry referring AMCL, are you running it too?\n\n## UPDATE ##\n\n\
    I run some test on your bag data. This the result of odometry test:\n\n![image\
    \ description](https://ftp.osuosl.org/pub/ros/download.ros.org/downloads/se_migration/ros/14279897427840711.tiff)\n\
    \nSince you are working in large environment (I measured abut 5 meters square\
    \ room) you can be happy about it! Any way I suggest you to follow this [guide](http://wiki.ros.org/navigation/Tutorials/Navigation%20Tuning%20Guide)\
    \ (if you already didn't): it will help you not only to improve your robot performances\
    \ but you can also learn something about navigation stack in ROS.\n\nBTW I ran\
    \ GMapping with the parameters I suggested and, actually, I reproduced the same\
    \ problem you claim about (sorry, my environment is not so large so I never experienced\
    \ it!). Fortunately the solution is easy. Set following parameters:\n\n    odom_frame:\
    \ odom \n    delta: 0.025\n    minimumScore: 50\n    maxRange: 5.5\n    maxUrange:\
