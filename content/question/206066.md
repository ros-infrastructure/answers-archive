  body_markdown: "As `catkin` wraps CMake, it should be possible to use 'all' the\
    \ debug options `cmake` supports ('all' is in quotes, as it's not a lot). From\
    \ the `cmake` [manpage](http://www.cmake.org/cmake/help/v3.0/manual/cmake.1.html)\
    \ (this is for 3.0, but it's mostly the same for older versions):\n\n    -Wdev\n\
    \        Enable developer warnings.\n        Enable warnings that are meant for\
    \ the author of the CMakeLists.txt files.\n    \n    --debug-output\n        Put\
    \ cmake in a debug mode.\n        Print extra stuff during the cmake run like\
    \ stack traces with message(send_error )\n        calls.\n    \n    --trace\n\
    \        Put cmake in trace mode.\n        Print a trace of all calls made and\
    \ from where with message(send_error ) calls.\n\nPass these either with `--cmake-args\
    \ ..` through `catkin_make`, or do a `mkdir build; cd build; cmake --DEBUG-OPTION\
    \ ../src` (the latter does not use Catkin, so you could use that to see whether\
    \ `catkin` itself is perhaps doing something different / unexpected).\n\nPS: afaik,\
    \ CMake employs a system similar to plain `make` for checking whether it should\
    \ re-run it's configuration step. The last time a `CMakeLists.txt` was changed\
    \ is a factor in this. If filesystem timestamps are 'somehow' not in sync with\
    \ your local system clock (ie: they are 'from the future'), I think CMake would\
    \ keep rerunning its configuration step at each invocation. I can't think of a\
    \ way where that would happen with *each* invocation though (unless someone/something\
    \ is changing the clock all the time).\n\nThe above is probably not happening\
    \ on your system, but I wanted to mention it just in case.\n"
