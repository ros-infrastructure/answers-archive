  body_markdown: "# Profiling an application #\n\nThis readme is a step by step application\
    \ for using VTUNE to profile a node.\n\n**General Overview**\n-----\nIn order\
    \ to profile your application, you will need to do the following:\n\n1. Edit the\
    \ application CMakeLists.txt to compile it correctly for profiling\n1. Edit the\
    \ application to add any user instrumentation\n1. Edit the application launch\
    \ file in order to launch it under the profiler with desired profile type\n1.\
    \ Edit the launch point of the application to set the timeouts longer\n1. Set\
    \ the correct settings in the pc to allow user profiling\n1. Run the node\n1.\
    \ View the profiler results with the VTune GUI\n\nWe will go through these step\
    \ by step here. \n\n**CMakeLists.txt**\n-----\nThere are a few changes for your\
    \ application binary that allow it to be profiled. \n\n\n    #  README: This is\
    \ an example CMakeLists.txt for adding a target that you intend to profile. It\n\
    \    #  is a mix of the regular catkin for ros stuff as well as the extra stuff\
    \ you need for the \n    #  actual profiling bit. Each bit will be explained below.\n\
    \    \n    # Regular ROS stuff, as required for all ros nodes.\n    cmake_minimum_required(VERSION\
    \ 3.2)\n    project(profiler_example)\n    \n    set(CMAKE_CXX_STANDARD 17)\n\
    \    set(CMAKE_CXX_STANDARD_REQUIRED YES)\n    \n    find_package(catkin REQUIRED\
    \ COMPONENTS\n      roscpp\n    )\n    \n    find_package(Threads REQUIRED)  #\
    \ Threads may or may not be required. For the profiler, the target that you link\
    \ against  \n                                    # will need to be linked against\
    \ threads if it uses threads. For basically any ros node\n                   \
    \                 # this will be the case because of subscription queues etc.\
    \ \n    \n    \n    catkin_package()\n    \n    set(THREADS_PREFER_PTHREAD_FLAG\
    \ ON) # This is just for us, we do prefer pthreads on our system, because linux\
    \ etc. We\n                                        # want this to ensure that\
    \ we use pthreads which are profilable. Very high chance\n                   \
    \                     # we are using them anyway.\n    \n    add_executable(test_profiler\
    \     # We add our executable as per usual, with all the translation units included.\
    \ \n        thread_profile_example.cpp\n    )\n    \n    #  The following 2 lines\
    \ are very important if you wish to use the user instrumentation API detailed\
    \ here:\n    #  https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/api-support/instrumentation-and-tracing-technology-apis/instrumentation-and-tracing-technology-api-reference.html\n\
    \    #  This is so you can include and then link against their libs. For very\
    \ basic example usage, see the thread_profiling_example.cpp\n    target_include_directories(test_profiler\
    \ PRIVATE /opt/intel/oneapi/vtune/latest/sdk/include) \n    target_link_directories(test_profiler\
    \ PRIVATE /opt/intel/oneapi/vtune/latest/sdk/lib64)\n    \n    # Each of the compiler\
    \ options and libs we are linking against are quite important, so they will be\
    \ detailed one at a time. \n    target_compile_options(test_profiler PRIVATE\n\
    \        -g                          # The most important, this compiles your\
    \ application with profiling symbols.\n        -fno-omit-frame-pointer     # This\
    \ adds some extra information that allows the vtune application to more easily\
    \ view your profile. \n        -D_LINUX                    # This is suggested\
    \ by Vtune, i don't know what this does.\n        -fno-asm                   \
    \ # This stops you from ending up with no code trace I think.\n    )\n    \n \
    \   target_link_libraries(test_profiler PRIVATE \n        ittnotify          \
    \ # This is important to link against if you are using the user API, see above\
    \ include directories\n        dl                  # This allows the dynamic linking\
    \ of the user api.\n        pthread             # This or the below must be linked\
    \ if you are using threads. Adding both doesn't hurt. \n        Threads::Threads\
    \    # See above.\n        ${catkin_LIBRARIES} # Normal ros linking.\n    )\n\
    \    \n    # Below is more regular ROS stuff\n    add_dependencies(test_profiler\
    \ ${catkin_EXPORTED_TARGETS})\n    \n    install(TARGETS \n        test_profiler\n\
    \    \n        ARCHIVE DESTINATION ${CATKIN_PACKAGE_LIB_DESTINATION}\n       \
    \ LIBRARY DESTINATION ${CATKIN_PACKAGE_LIB_DESTINATION}\n        RUNTIME DESTINATION\
    \ ${CATKIN_PACKAGE_BIN_DESTINATION}\n    )\n\n\nThe details for how to do this\
    \ were taken from the [compiler switches for linux](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/set-up-analysis-target/linux-targets/compiler-switches-for-performance-analysis-on-linux-targets.html)\
    \ vtune page. It is also helpful to look at the makefile in the provided matrix\
    \ example in `/opt/intel/oneapi/vtune/latest/samples/en/C++/matrix`.\n\n**Adding\
    \ user API instrumentation** \n-----\nDetails about how to do this are [here](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/api-support/instrumentation-and-tracing-technology-apis/instrumentation-and-tracing-technology-api-reference.html),\
    \ with the most useful ones so far being:\n1. [One time user events](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/api-support/instrumentation-and-tracing-technology-apis/instrumentation-and-tracing-technology-api-reference/event-api.html)\n\
    2. [Thread naming](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/api-support/instrumentation-and-tracing-technology-apis/instrumentation-and-tracing-technology-api-reference/thread-naming-api.html)\n\
    \nBut you can do pretty much anything. \n\n**Launching from a launch file**\n\
    -----\nIn order to profile a node being launched from the ROS ecosystem you need\
    \ to do a couple of things. \n\nThe first is to amend the launch file with a prefix\
    \ to launch the profiler. You do this with:\n\n```\nlaunch-prefix=\"\n  /opt/intel/oneapi/vtune/2021.4.0/bin64/vtune\
    \              # Always give the full path, the environment is not set up the\
    \ way you think.\n  --collect hotspots                                       \
    \ # Specify the type of profile you want to make\n  -knob sampling-mode=hw -knob\
    \ stack-size=0                 # Specify extra arguments, like use hw mode.\n\
    \  -result-dir /tmp/profiling/little-test-@@@   # Specify the output directory,\
    \ @ is an auto incrementing numeral.\n  \"\n```\n\n*Note:* This all needs to be\
    \ a single line without comments. \n\nThe full command line interface documentation\
    \ is [here](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/command-line-interface/running-command-line-analysis.html).\
    \ These are my recomendations:\n- Use hw sampling mode, it has a smaller impact\
    \ and gets more samples. \n- There are many different profilers you can run, there\
    \ is a list [here](https://software.intel.com/content/www/us/en/develop/documentation/vtune-help/top/command-line-interface/running-command-line-analysis.html)\n\
    - The easiest way to get a complex command line is to select the items you want\
    \ with the GUI and check the generated command line. When you create a new profiler\
    \ action in the gui, next to the start (play) button, there is a button to show\
    \ you the command line of what you are about to run. \n- The vtune profiler needs\
    \ significant time to finalize the result and make a report. If you want this\
    \ to occur, you need to add some extended timeout to the launch so that it doesn't\
    \ send SIGTERM to bomb your application while it is finalizing. You can add `--sigint-timeout=60\
    \ --sigterm-timeout=60` to any launch command to extend this death time. It is\
    \ likely that you will want to add it to `node_manager.py` where most launch files\
    \ are run.\n\n**Changing your environment**\n-----\nYou need a bunch of different\
    \ environment variables. Likely that you will need to play with this for your\
    \ specific example, eg. your user may not always be root or something. \n\n```\n\
    echo \"source /opt/intel/oneapi/setvars.sh\" >> /home/user/.bashrc\nsed -i 's/ptrace_scope\
    \ = 1/ptrace_scope = 0/g' /etc/sysctl.d/10-ptrace.conf\necho \"echo 0 > /proc/sys/kernel/perf_event_paranoid\"\
    \ >> /home/user/.bashrc\necho \"export INTEL_LIBITTNOTIFY32=/opt/intel/oneapi/vtune/latest/lib32/runtime/libittnotify_collector.so\"\
    \ >> /home/user/.bashrc\necho \"export INTEL_LIBITTNOTIFY64=/opt/intel/oneapi/vtune/latest/lib64/runtime/libittnotify_collector.so\"\
    \ >> /home/user/.bashrc\n```\n\n**Running the stack and getting results**\n-----\n\
    \nYou can see above:\n\n```\necho \"echo 0 > /proc/sys/kernel/perf_event_paranoid\"\
    \ >> /root/.bashrc\n```\n\nIf the user is not privileged, you may need to do:\n\
    \n```\nsudo sysctl -w kernel.perf_event_paranoid=1\n```\n\nIf you have set up\
    \ everything correctly so far, you should just be able to run the system and expect\
    \ the results to be generated at the location where you specified in the launch\
    \ file (using `-result-dir`). \n\nNow you can simply use vtune-gui top open the\
    \ results. Use `ctrl-o` and go to the result folder and open the `.vtune` file.\
    \ Happy profiling!\n\n**Attaching to an existing process with PID**\n-----\n*Currently\
    \ this does not fully work* - see current bug report [here](https://community.intel.com/t5/Analyzers/Get-user-events-from-VTune-doesn-t-work-with-attach-to-process/m-p/1294212/emcs_t/S2h8ZW1haWx8dG9waWNfc3Vic2NyaXB0aW9ufEtRSE83S1JOMlVMWDI0fDEyOTQyMTJ8U1VCU0NSSVBUSU9OU3xoSw#M20844).\n\
    - The collection of user functions and system functions is correct.\n- The collection\
    \ of user API is not working, aka, ITT events and thread names will not appear\
    \ in the profiler data. \n\nYou can use `-target-pid` to attach to a process already\
    \ running to capture profiler output. The application needs to be started in an\
    \ environment where the envrionment variables `INTEL_LIBITTNOTIFY32` and `INTEL_LIBITTNOTIFY64`\
    \ are set with the correct dll path. You can find your process with `ps -aux`\
    \ or if you know the name already issue a command like:\n\n```\n/opt/intel/oneapi/vtune/2021.4.0/bin64/vtune\
    \ \\\n    --collect hotspots -knob sampling-mode=hw -knob sampling-interval=0.5\
    \ -knob stack-size=0 \\\n    -result-dir /tmp/docker_share/profiling/test-@@@\
    \ \\\n    -target-pid $(ps -ef | grep example | head -n 1 | awk '{print $2}')\n\
    ```\n\nThe last line will find the pid for you (ensure that your process name\
    \ is unique, otherwise just find it yourself). \n\n"
