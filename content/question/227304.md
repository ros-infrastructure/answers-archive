  body_markdown: "**Update**\n\nI have an rviz plugin that subscribes to an image\
    \ topic and allows the user to specify the scale and the tf that the image ought\
    \ to be aligned to:\nhttps://github.com/lucasw/rviz_textured_quads\n\nVideo example\
    \ of a webcam on a quad inside rviz:\nhttps://www.youtube.com/watch?v=RzT0tkuJkwA\n\
    \nI've tested it in jade and kinetic.\n\nIt was forked from another project that\
    \ adapted code and made a standalone version of the texture mesh code from vigir_ocs_rviz_plugins\
    \ mentioned below.\nIt uses a texture projection method rather than (the probably\
    \ simpler) dynamic texturing above, but could be generalized to have non-rectangular\
    \ shapes to project onto (like provide a mesh via a Marker or some other message).\n\
    \n**Old answer**\n\n[Rviz: Display image in 3D scene](http://answers.ros.org/question/218502/rviz-display-image-in-3d-scene\
    \ ) had a suggestion to use a custom mesh display plugin developed for the DRC\
    \ by the Vigir team.\n\nI attempted just that https://github.com/lucasw/vigir_ocs_common/tree/master/vigir_ocs_rviz_plugins/vigir_ocs_rviz_plugin_mesh_display_custom\
    \ but haven't gotten it working (but also haven't spent much time on it).  They\
    \ also had a forked rviz that some of the nodes in the original repo needed, hopefully\
    \ not this one too.  \n\nThe point of the plugin was to project a texture onto\
    \ an arbitrary mesh, which is cool, but overkill for you and that other question-\
    \ a custom plugin that just creates a textured quad at a rviz property defined\
    \ tf and size and updates the texture via Image topic would be great.\n\nTake\
    \ a look at [any rviz plugin](https://github.com/ros-visualization/rviz/tree/indigo-devel/src/rviz/default_plugin/markers)\
    \ and it is all raw Ogre inside them.  The pitfalls are that code lives in a plugin\
    \ environment, so rviz has control of global settings and making the main calls\
    \ to Ogre which have to be respected, and it is possible to do screwy things within\
    \ a plugin that mess up rendering in the entirety of rviz.\n\nI imagine performance\
    \ is poor, but if your state doesn't change that quickly it maybe is sufficient\
    \ to load a textured mesh in a standard mesh resource rviz Marker, and updating\
    \ the texture on disk and resending the Marker as needed from another node. \n\
    \n[marti_visualization_msgs/TexturedMarker](http://docs.ros.org/api/marti_visualization_msgs/html/msg/TexturedMarker.html)\
    \ is only for mapviz, at first I thought there was an rviz plugin to show it."

Hey all,

I'm looking at building an rviz plugin which would display [the state of OTTO's programmable LED strip](http://www.clearpathrobotics.com/otto-materials-handling-industrial-vehicle/#video). I'm pretty sure I don't want to create 300+ new pieces of single-colour geometry, so I'm wondering about the feasibility of supplying a single geometry for the strip as a whole, and then texturing it at runtime from a plugin.

I found some info on doing this in Ogre here: http://ogre3d.org/tikiwiki/Creating+dynamic+textures

But I'm wanting to get a general sanity check on what the pitfalls are going to be with this approach. How possible is it to mix native Ogre calls in with rviz's geometry? Is there another plugin which demonstrates something like what I'm wanting to do here?
