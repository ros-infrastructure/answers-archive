    \ and SDF look close enough such that you should be able to transform one to another\
    \ (SDF is actually more complete than URDF). Then for your first question:\n\n\
    - I made a SDF world file that contains a simple arm robot model and some basic\
    \ objects. In this file I link the arm to a ModelPlugin and the world to a WorldPlugin.\
    \ To do so, the [tutorials](http://gazebosim.org/tutorials) of gazebo are clear\
    \ and straight forward.\n\n- In the ModelController, which is a C++ class, I use\
    \ a class called JointController, you can find the [class reference](http://osrf-distributions.s3.amazonaws.com/gazebo/api/dev/classgazebo_1_1physics_1_1JointController.html)\
    \ but impossible to find any example on the web. To move a joint you can then\
    \ use a [PID](https://osrf-distributions.s3.amazonaws.com/gazebo/api/dev/classgazebo_1_1common_1_1PID.html),\
    \ it would be something like this (in this case I make a pointer to the JointController\
    \ as a property of the RobotControl class to be able to call it at each iteration):\
    \ \n\n<pre><code>\n#include &lt;boost/bind.hpp&gt;\n#include &lt;gazebo/gazebo.hh&gt;\n\
    #include &lt;gazebo/physics/physics.hh&gt;\n#include &lt;gazebo/common/common.hh&gt;\n\
    #include &lt;stdio.h&gt;\n#include &lt;math.h&gt;\n\nnamespace gazebo\n{\n  class\
    \ RobotControl : public ModelPlugin\n  {\n    // Pointer to the model\n    private:\
    \ physics::ModelPtr model;\n\n    // Pointer to the world\n    private: physics::WorldPtr\
    \ world;\n\n    // Pointer to the update event connection\n    private: event::ConnectionPtr\
    \ updateConnection;\n\n    private: physics::JointControllerPtr jointsController;\n\
    \n    // When the simulation starts\n    public: void Load(physics::ModelPtr _parent,\
    \ sdf::ElementPtr /*_sdf*/)\n    {\n      // Store the pointer to the model\n\
    \      this->model = _parent;\n      // Store the world\n      this->world = this->model->GetWorld();\n\
    \      // Create the joint controller\n      this->jointsController =  boost::shared_ptr<physics::JointController>(new\
    \ physics::JointController(this->model));\n      // Create a PID\n      common::PID\
    \ PID = common::PID(100, 100, 100, 1, -1, 1000, -1000); \t\t\n      // Get all\
    \ the joints of the model\n      std::vector<physics::JointPtr> joints = this->model->GetJoints();\n\
    \      // For each one of these joints\n      for (unsigned i=0; i < joints.size();\
    \ i++) \n      {\n        // Add it to the joint controller\n        this->jointsController->AddJoint(joints[i]);\n\
    \        // Set its PID values\n        this->jointsController->SetPositionPID(joints[i]->GetScopedName(),PID);\t\
    \n      }\n      // Listen to the update event. This event is broadcast every\n\
    \      // simulation iteration.\n      this->updateConnection = event::Events::ConnectWorldUpdateBegin(boost::bind(&ArmControl::OnUpdate,\
    \ this, _1));\n    }\n\n    // Called at each update of the simulation\n    public:\
    \ void OnUpdate(const common::UpdateInfo & /*_info*/)\n    {\n       // Set an\
    \ angle (here it is stupid since the angle doesn't change)\n      float angle\
    \ = 0.5 // gradient angle\n      this->jointsController->SetPositionTarget(this->model->GetJoint(\"\
    jointName\")->GetScopedName(),angle);\n    }\n  };\n  // Register this plugin\
    \ with the simulator\n  GZ_REGISTER_MODEL_PLUGIN(RobotControl)\n}\n</code></pre>\n\
    \n\nThe WorldPlugin is useful to add/remove objects in your simulation, or access/change\
    \ the properties of the simulation. \n\nI hope this helps.\n\nCheers\n    "

  body_markdown: " I am also using an evolution of robots in Gazebo, There are some\
    \ points that you have to take into account:\n\n 1. you can run gazebo in headless\
    \ mode, meaning without visualization, this will reduce computing time.\n 2. For\
    \ the simulation of robots (to evaluate them) you can:\n\n    2.1. for each generation\
    \ run on simulation (one world) that will contain the population, each robot in\
    \ a unique position\n\n    2.2. evaluate each robot independently in parallel,\
    \ for example if you have an 8 core cpu you can run 8 at once.  (not sure but\
    \ this will probably reduce computing time and this depending on complexity of\
    \ morphology) \n\n 3. Reset the simulation do not work, I mean that if we restart\
    \ the initial conditions and position of robot it will not give the same behavior\
    \ (robot with the same ANN), so this will not help for optimization. So I suggest\
    \ to quit and restart the simulation at each generation\n\n 4. Communication between\
    \ plugins is with publishers and subscribers. But there is some problem here that\
    \ will affect evolution. When you publish something in time x, the listener will\
    \ not receive the message instantly. it will receive it in time x or x+1 or x+2\
    \ or ... So, sometimes, when you want to use the message sent, and at this time\
    \ the message is not arrived yet you will read the previous message. \n\nI hope\
    \ that you get what I mean, and if you have any other question do not hesitate\n\
    \nps:I encountered those issues in Gazebo version 4.\n\n \n\n \n\n"
