I'm having an issue where, when there are a large number of subscribers to a topic, killing and restarting the node that publishes that topic results in several of the connections not re-establishing correctly.
I am able to reproduce this problem with a simple node that publishes continuously to a topic, and with 40 "rostopic echo"s that subscribe to that topic inside of the ROS Noetic docker that is provided as part of [this](https://github.com/dusty-nv/jetson-containers) repository (dustynv/ros:noetic-ros-base-l4t-r35.1.0). The ROS master is also running inside that same docker container.
After spinning up a ROS core, my publisher node, and 40 subscribers, if I kill and restart the publisher node, I see CPU usage for the publisher node spike for several seconds to 100%. Screenshot available [here](https://user-images.githubusercontent.com/124215357/216189905-e269a1fb-5a7b-4907-8ab4-84ccc74b0f7e.png). 

For 30-90 seconds after restarting the node, roswtf will indicate that several nodes that are supposed to be connected are not connected. The subscribers that aren't connected at the beginning will not receive messages from the publisher, and these initial messages will be lost. This creates problems with Nodelets, as their bonds often do not connect correctly between the nodelet and the nodelet manager, and the nodelet shuts down. Screenshot of roswtf output available [here](https://user-images.githubusercontent.com/124215357/216190331-5eece35e-4241-4ea8-ab17-1677241f3a0b.png)

In addition to this, sometimes a few subscribers will remain unconnected to the publisher seemingly indefinitely (>30 minutes), though that is more challenging to reproduce.

When running the same test code outside of a docker container on the Jetson, the connections recover from the restart almost immediately (<5s) and there is no spike in CPU usage when the node first starts up. Running this test in an x86 docker on a regular laptop gives the same results as outside of the docker on the Jetson.

This leads me to believe that something about either the way this particular docker image is configured, or something about running docker images on the Jetsons in general. I'm hoping to get some suggestions about what particular configuration differences could cause these issues, or what logs may be useful to look at to try to get to the bottom of this. 

I also posted this as an issue in the github for the docker container [here](https://github.com/dusty-nv/jetson-containers/issues/219).

I am happy to upload my docker image with these tests scripts if they will be helpful for someone willing to help debug this.
