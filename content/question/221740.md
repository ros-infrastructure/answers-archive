  body_markdown: "tf and tf2 are not runnable which is why it's hard to answer your\
    \ question. \n\ntf and tf2 are libraries which are integrated into your node or\
    \ nodelet. If you create a nodelet and use tf inside of it, you will get all the\
    \ speedups of working inside a nodelet.\n\nThere are some standalone executable\
    \ tools. However they are low bandwidth and I highly doubt that they will become\
    \ a bottleneck for your performance. \n\nUpdate: It looks like it's not actually\
    \ using the shard pointer when publishing. [here](https://github.com/ros/geometry_experimental/blob/5d34903e1f13aa2ab69e5964db38b58810f00a63/tf2_ros/src/transform_broadcaster.cpp#L60)\
    \ and [here](https://github.com/ros/geometry_experimental/blob/5d34903e1f13aa2ab69e5964db38b58810f00a63/tf2_ros/include/tf2_ros/transform_listener.h#L63)\
    \ A PR to fix that would be great. However before you try to optimize too much\
    \ you should really profile what's taking your time. \n\nIt's much more likely\
    \ that avoiding multiple listeners such as using a buffer server and buffer client\
    \ will be a way to save a lot more resources. [an example usage](https://github.com/ros/geometry_experimental/blob/5d34903e1f13aa2ab69e5964db38b58810f00a63/test_tf2/test/test_buffer_client.cpp)\
    \ A buffer server is [very simple to setup](https://github.com/ros/geometry_experimental/blob/5d34903e1f13aa2ab69e5964db38b58810f00a63/test_tf2/test/test_buffer_server.cpp)\
    \ This has the highest payoff for low frequency scripts which just need to poll\
    \ tf infrequently and are tolerant of higher latency calls. "
