ROS2 typesupport_fastrtps message generation looks in wrong location for tinyxml2.so when using CMAKE_SYSROOT

I'm cross-compiling a ROS2 workspace for arm64 on an amd64 platform. I've created a sysroot containing the workspace dependencies. Note that I am not building the ROS2 core from source, I am only building a few small toy packages, after having exported a sysroot that has their dependencies installed (e.g. amentcmake, rclcpp, rclpy, rosidldefaultgenerators, rosidldefaultruntime) Using the below toolchain, I am able to build simple packages depending on rclcpp or rclpy, but a package using rosidl to generate messages looks for tinyxml2 in the host root, rather than the target sysroot. (example package is called `ccmsgs`.

make[2]: *** No rule to make target '/usr/lib/aarch64-linux-gnu/libtinyxml2.so', needed by 'libcc_msgs__rosidl_typesupport_fastrtps_cpp.so'.  Stop.

My question is, how can I discover where this path is being generated so that I can fix it to find tinyxml2 in the correct location?

The library in question does exist in the target sysroot, and all other needed libraries are being discovered there

$ ls /sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so
/sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so

The toolchain file looks like the following

set(PY_VERSION 38)

set(SYSROOT /sysroot)

# Generic

require_env(SYSROOT)

colcon build \
  --cmake-args -DCMAKE_VERBOSE_MAKEFILE:BOOL=ON -DCMAKE_TOOLCHAIN_FILE=/toolchains/aarch64-gnu.cmake --no-warn-unused-cli

This suggests that the issue is something to do with system-level libraries using absolute rather than relative symlinks, which are then resolved to look on the host system.

Answers

I was running into a two-part problem here, for those who run across this question:

  1. Absolute symlinks in the target sysroot. This is remedied using the symlinks utility https://linux.die.net/man/8/symlinks within the sysroot before exporting it for use.
  2. Fast-RTPS is exporting a dependency as an absolute path in its built debian installation. I have reported this issue here https://github.com/eProsima/Fast-DDS/issues/1264 and can manually work around it by symlinking the offending library

ln -s sysroot/usr/lib/aarch64-linux-gnu/libtinyxml2.so /usr/lib/aarch64-linux-gnu.so

This effectively resolves the problem for this case, though a resolution of the reported packaging bug will be better.
