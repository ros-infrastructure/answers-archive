I believe that the short answer to your question is that what you're looking for does not exist because it was designed that way.

Walking the tree is something that we have specifically designed out of any runtime interaction or buildsystem interaction. The only place that it's needed is in the build tool, ala colcon, because each package should exist and work as a standalone package, and should not know or care about anything outside of it's path. The buildsystem can be invoked on that package alone without knowing or caring about the checkout or delivery method, just that it's dependencies have been installed and sourced first.

The build tool is exactly the thing that finds packages, checks their dependency order and invokes them in the topologically required order. Where you as the user could do that manually but it would be a lot of typing and error prone.

The build tool can also be used for running unit tests including thing linters such as ament_lint which are run on a per package basis. The linting of any individual package should not effect packages nearby on the filesystem unless they're a dependency and in that case they should have already been installed and available.

For your use case I would suggest that you bump up a layer and instead of running ament_clang_tidy with a filter so that it skips running for other packages instead you use the build tool to select the packages from that repository and selectively invoke ament_clang_tidy explicitly on the packages you want to test. (Having used colcon list or other mechanism's to explicitly find said list based on the repository).
