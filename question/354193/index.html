Hi @prithupareek,

I think in my humble opinion that you should change your current paradigm since I think it is not coherent with the "modular" approach of ROS.

I would generate different nodes for what you are trying to do to keep it simple and less error prone. You can implement two nodes for the client-server action lib communication and a last node implementing a Model plugin that reads from the command topic from the actionlib server. With that subscriber you will able to extract command data from ROS actionlib and apply the necessary commands on your gazebo model. I have never try to include a actiolib server into a Gazebo plugin but this is because, for me, there is no point in running both at the same scope since actionlib was not designed with that in mind; one of the most important reason may be that the actionlib server needs a ros::spin and by definition that instruction is a blocking procedure.
