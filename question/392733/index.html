Hi,

from my first experience this may be due to one or more joints having >360° valid range, e.g. in my case the last joint can make several full rotations. Apparently, when setting a new pose goal from a given goal, the IK for the final pose is solved without optimizing the joint angle movement with respect to the current state (e.g. minimizing the changes on all joint angles), so it creates a random solution from the list of periodic solutions even if the new goal is immediately next to the current position.. and then creates a smooth path to do it with some artistic loops.

I had success with two approaches (using Python, but that shouldn't matter). Both don't appear to be optimal, though: a) setting up joint constraints for the move (that's different to limiting the joint valid range): 

  joint_constraint = JointConstraint()
  joint_constraint.joint_name = "joint_6"
  joint_constraint.position = 0.0  # should we use the current angle instead of "any valid"?
  joint_constraint.tolerance_above = pi/2   # in total 180°- we should keep <<360° to avoid 2 solutions for the same pose
  joint_constraint.tolerance_below = pi/2   # is this relative around position or absolute?
  joint_constraint.weight = 1.0
  constraints.joint_constraints.append(joint_constraint) # Append the constraint to the list of contraints
  arm.set_path_constraints(constraints)    # Set the path constraints on the arm
  # ...
  arm.plan()

This works but since documentation of the constraints remains unclear to me, I didn't trust it 100% yet. What is the interpretation of the fields? Are the above and below values absolute limits or a tolerance around the position field? Would it still work if I set a narrow constraint and the robot is currently not within that range (e.g. I would like to freeze one DOF to 0.0 with 0 tolerance in some situations)

b) Therefore I added a 2nd level and check/reject the trajectory before it is executed. That's an ugly solution, though, as in my case the only observed error is in the joint states of the end pose and the planning time is wasted. Something like:

arm.set_pose_target(target_pose) 
traj = arm.plan() # traj may choose a valid random solution for the end pose 
if traj.joint_trajectory.points:
  ok = False
  while not ok:
    joint_6_val = traj.joint_trajectory.points[-1].positions[5]
    if abs(joint_6_val) > pi:
      traj = arm.plan()   # the next solution is typically completely different !
    else:
      ok = True
  arm.execute(traj)

This works because the entire planning relies on random sampling for most solvers such as RRTConnect

I think the best solution would be to c) calculate the target pose joint state first, then find potential valid 360°-periodic solutions, modify the joint state goal, and do the planning with this fixed goal. Currently this seems to be possible only by using setJointValueTarget and getJointValueTarget, I am not aware that such approach could be "hidden" e.g. by registering a callback function which is executed by plan(). I don't know if the existing constraint system would already allow this as it comes close to the callback idea - just that we would need a priorization that an optimization of the IK solution for the target pose should happen before any trajectory planning is done.

From what I see so far, we have JointConstraints, PositionConstraints, OrientationConstraints and VisibilityConstraints. If my understanding is correct, JointConstraints would limit the absolute angle of a joint along the entire path, but it would not fix an initially bad solution for the IK? In the general case I would not like to restrict the joints to <360°. There may be cases where this is totally valid (say, for fixing a screw, or for working out a solution around an obstacle) - however, when not explicitly requested to make full turns, the angle change between start and target should be minimized from the range of periodic solutions. Such constraint does not seem to exist yet?

A new type of constraint might also be useful to avoid state "flips" along the path, though I am not deep enough into this topic yet to say how ;) I think the first information required would be to know the number of possible solutions and to bring them in some kind of order to be able to reliably prefer one such as "elbow down"). That's certainly harder than choosing from a periodic solution. It might perhaps help if the solvers could change their "randomness" and explore the space from one chosen end of the valid range (e.g. the end we're currently closer to, in order to allow all solutions but to just avoid extra flips - just a speculation, not sure if this could work)?
