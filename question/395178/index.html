    moveit::planning_interface::MoveGroupInterface::Plan my_plan;

    // get the current set of joint values for the group.
    std::vector<double> joint_group_positions;

    // Now, let's modify one of the joints
    joint_group_positions[0] = tau/6;  // -1/6 turn in radians
    move_group_interface.setJointValueTarget(joint_group_positions);

    move_group_interface.setMaxVelocityScalingFactor(0.05);
    move_group_interface.setMaxAccelerationScalingFactor(0.05);
    move_group_interface.setStartStateToCurrentState();

    std::cout<< "desired position: " << joint_group_positions[0] << std::endl; 
    if(success){

    return 0;

Asked by mp on 2022-01-28 08:56:03 UTC

The velocity limits likely come from the URDF, which has them directly from the datasheet provided by KUKA. I doubt they are different, unless your KRC has lower limits configured for whatever reason.

Personally, I would check acceleration instead.

The URDF does not contain any data on acceleration limits, and it's likely joint_limits.yaml says has_acceleration_limits: false for all joints. Unless something has changed, that will cause MoveIt to use 1.0 rad/s^2, which is rather slow.

KUKA does not tell anyone the acceleration limits, so you'll have to guestimate some and update your joint_limits.yaml.

But all of this is likely not connected to your actual problem. As I wrote earlier, if the trajectory execution manager aborted a trajectory, it should print an ERROR on the console. You don't mention any.

Something makes MoveIt conclude trajectory execution completed already. From your earlier test, it seems the driver is OK. You want to figure out what is in between.

Asked by mp on 2022-01-31 08:38:04 UTC

TEM == MoveIt's Trajectory Execution Manager.

It's the part of MoveIt which (among other things) looks at the time it takes a controller to execute a trajectory and compares it to the expected duration. If expected < actual, depending on its configuration, it will ABORT the executing trajectory (as it's likely there is something wrong).

You report actual times of up to 2 * expected. Without custom configuration, I would have expected the TEM to have ABORTed your trajectory.

But you state the robot does end up at the goal pose, and you don't report any ABORTed trajectories (see my earlier comment about the log lines you should see).

Asked by Nodrog on 2022-04-26 02:18:41 UTC

moveit seems to always assume [..]

nit, but: MoveIt doesn't assume anything. It only 'knows' what you tell it.

If the robot is capable of updating its joint limits at runtime, and you don't tell MoveIt about this, there are going to be different expectations.

Note that MoveIt does not use time to calculate when your goal should be complete. Only the driver can mark the goal as complete, and at that point MoveIt will trust your driver.

So if you write:

the issue is to do with setting the run speed on the robot controller, moveit seems to always assume a 100% run speed regardless of what the robot controller is set at

that makes me suspect the driver is doing something it shouldn't.

Not MoveIt.
