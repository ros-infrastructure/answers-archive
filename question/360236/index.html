In order to link the rs camera_odom_frame to the robot base_link, I have written a custom tf broadcaster. Basically I know the tf between the base_link --> camera_link and the rs generates camera_link --> camera_odom_frame. Using this information I am able to derive the tf base_link --> camera_link. Below is the code that I use to broadcast the new generated tf. A very identical node is written to generate base_link --> zed_map tf.

int main(int argc, char** argv){
    ros::init(argc, argv, "rs_tf_broadcaster");
    ros::NodeHandle node;

    tf::TransformListener listener;

    ros::Rate rate(200.0);
    while (node.ok()){

        tf::StampedTransform lu_tf;
        try{
            listener.waitForTransform("camera_link", "camera_odom_frame",ros::Time::now(), ros::Duration(4.0));
            listener.lookupTransform("camera_link","camera_odom_frame",
                                    ros::Time(0), lu_tf);
        }

        catch (tf::TransformException ex){
            ROS_ERROR("%s",ex.what());
            //ros::Duration(1.0).sleep();
        }
        tf::Transform base_to_rsbase_tf;
        tf::Quaternion q_rs;
        q_rs.setRPY(0, 0.83, 0);
        tf::Vector3 vec3_rs(0.265, 0.12, 1.0);

        base_to_rsbase_tf.setOrigin(vec3_rs);
        base_to_rsbase_tf.setRotation(q_rs);

        tf::Transform rsbase_to_rsodom_tf;
        rsbase_to_rsodom_tf.setOrigin(lu_tf.getOrigin());
        rsbase_to_rsodom_tf.setBasis(lu_tf.getBasis());

        tf::Transform base_to_rsodom_tf;
        base_to_rsodom_tf = base_to_rsbase_tf * rsbase_to_rsodom_tf; //VERIFIED

        static tf::TransformBroadcaster br_rs;
        br_rs.sendTransform(tf::StampedTransform(base_to_rsodom_tf, ros::Time::now(), "base_link", "camera_odom_frame"));

        rate.sleep();
    }
  return 0;
};

"Any odom ... its own tree": I dont think this is correct. You would fuse the two datastreams (odometry messages) to transform the one odom-frame in a fusion node. Some nodes have tf publishing as feature but it is optional(and mostly usefull). If you want to use the node data and take care of its integration into the tf tree thats fine. tf is not the main datastream its higher level as it already incorporates the pose and reference frame.

If you have a map - odom - baselink tree and odom message tells you your at position x 1.0, if then the localization(odom correction node) "tells" tf there is an error of x 0.2, tf (transform pose odom frame) will show x1.2. The pose changes but not the message data sent by odom node. The tf tree is not a direct representation of all published topics. If you have 2 links in the urdf but 4 encoders publishing data, the tf tree only has 2 frames.

Your welcome. I still think its about misunderstanding tf. the odometry message just tells you that the base moved x 0.5 for example. It has no clue about frames, thus you can have two sources, fuse their data and interpret the fused data in map space, thats the tf part, interpreting different data in a single defined space. If you have a simple robot arm with two links and joints(only up and down joints), if both sensors give you -45° the tf pose of the second link ("endeffektor"), will be the added up -90°.
